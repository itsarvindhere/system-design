Back of the Envelope Estimation means doing rough calculations quickly to understand the scale of a system.

In system design interviews, we do not need exact numbers. We need reasonable estimates. For example -

    1. How many requests per second will the system receive?
    2. How much storage will be needed?
    3. How much bandwidth will be used?
    4. How many servers may be required?
    5. How much cache memory may be needed?

These estimates help us make better design decisions.

# WHY DO WE NEED ESTIMATION?

System Design decisions depend on the scale.

A system with 1000 users can be simple. A simple with 100 Million users needs a very different design.

For example -

    1. If the read traffic is heigh, we may need caching
    2. If the write traffic is high, we may need sharding
    3. If the storage is huge, we may need object storage or distributed databases.
    4. If latency must be low globally, we may need CDN or multi-region deployment.

Without estimation, we may design blindly.

So, the back of the envelope estimation gives us a rough sense of the problem size.

# WHAT TO ESTIMATE?

In system design interviews, we commonly estimate these things -

    1. Users
    2. Requests per second
    3. Read/Write ratio
    4. Storage requirement
    5. Bandwidth requirement
    6. Cache requirement
    7. Database size
    8. Number of servers
    9. Message queue throughput

We do not always estimate everything. We estimate what matters for the problem.

For example, in a URL Shortener, storage and redirect QPS (Queries per second) matter.

In a video streaming system, storage and bandwidth matter a lot.

In a chat system, concurrent connections and message throughput matter.

## USEFUL TIME CONVERSIONS

Here are some numbers that are worth remembering -

    1 day = 24 hours
    1 hour = 60 minutes
    1 minute = 60 seconds
    1 day = 86,400 seconds

For rough estimation, we often use -

    1 Day = 100,000 seconds

THis makes mental math easier.

For example -

    100 Million requests per day
        = 100,000,000 / 100,000
        = around 1,000 requests per second

This is not exact, but good enough for interviews.

Here are some useful storage conversions -

    1 KB = 1 thousand bytes
    1 MB = 1 million bytes
    1 GB = 1 billion bytes
    1 TB = 1 trillion bytes
    1 PB = 1 thousand TB

In exact binary terms,these are slightly different. But, for system design interviews, decimal approximations are usually fine.

## REQUESTS PER SECOND (RPS)

Requests per second tells us how many requests the system receives every second. 

    Requests per second = total requests per day / seconds per day

For quick math -

    Requests per second = total requests per day / 100,000

For example -

    10 Million requests per day
    10,000,000 / 100,000 = 100 requests per second

So, 10 million requests per day is roughly 100 RPS.

## PEAK TRAFFIC

Average traffic is not enough. Real systems have peak traffic. For example, average traffic may be 1,000 RPS, but during peak hours it may become 5,000 RPS.

A common rough assumption -

    Peak traffic = 2x to 10x average traffic

For example -

    Average RPS = 1,000
    Peak Factor = 5

    Peak RPS = 5,000

We should design for peak traffic, not only average traffic.

## READ/WRITE RATIO

Many systems have different read and write traffic. For example, in a URL shortener -

    Creating short URLs = writes
    Opening short URLs = reads

Usually, reads are much higher than writes. For example -

    Total traffic = 10,000 RPS
    Read/write ratio = 100:1

This means -

    Reads = around 9,900 RPS
    Writes = around 100 RPS

This tells us caching will be useful.

For a chat system, write traffic may be high because users send messages.

For a news feed, reads may be much higher than writes.

Understanding read/write ratio helps us choose caching, replication, sharding, and database design.

## STORAGE ESTIMATION

Storage estimation means calculating how much data the system will store.

Formula -

    Storage = number of records * size of each record

For example -

    100 Million users
    Each user record is lets say 1 KB

    Storage = 100 Million * 1 KB = 100 GB

Another example is -

    1 Billion messages per day
    Each message = 1 KB

    Daily storage = 1 billion KB = 1 TB per day

If we store data for 1 year -

    1 TB * 365 = 365 TB

This tells us we need a serious storage strategy.

## BANDWIDTH ESTIMATION

Bandwidth means how much data is transferred over the network. 

    Bandwidth = Requests per second * Response Size

For example -

    10,000 requests per second
    Average response size = 100 KB

    Bandwidth = 10,000 * 100 KB = 1,000,000 KB per second
    OR 1 GB per second

This is important for systems that serve images, videos, files or large API responses.

For example, in video streaming, bandwidth is usually more important than request count.

## CACHE ESTIMATION

Cache Estimation means calculating how much memory we need to cache hot data. A common idea is the 80/20 rule -

    20% of the data may receive 80% of traffic

For example -

    Total Data = 10 TB
    Hot Data = 20%

    Cache needed = 2 TB

But in many interviews, we use more practical assumptions.

For example -

    1 Million popular URLs
    Each mapping = 500 bytes

    Cache size = 1 Million * 500 bytes = 500 MB

So, a small cache may handle a lot of traffic if access patterns are skewed.

## SERVER ESTIMATION

Server estimation is usually very rough.

Formula -

    Number of servers = total QPS / QPS per server

For example -

    Peak Traffic = 50,000 QPS
    One server can handle 5,000 QPS

    So, servers needed = 50,000 / 5,000 = 10 servers

Then, add extra capacity for safety.

For example -

    Required servers = 10
    Add buffer = 30%

    Final = around 13 servers

In interviews, do not over-focus on exact server count.

The goal is to show that you understand capacity planning.

# EXAMPLE - CHAT SYSTEM

Assume -

    50 million daily active users
    Each user sends 20 messages per day

Messages per day -

    50 million * 20 = 1 billion messages per day

Messages per second -

    1 billion / 100,000
    = around 10,000 messages per second

If peak is 5x -

    Peak message rate = 50,000 messages per second

Storage -

    Average message size = 1 KB

    1 billion messages * 1 KB
    = 1 TB per day

For 1 year -

    365 TB per year

From all this, we may conclude that -

    Write throughput is important.
    Storage grows quickly.
    Message ordering matters.
    Database partitioning may be needed.
    Real-time delivery may need WebSockets.
    Old messages may need archival storage.

Back of the envelope estimation helps us design with scale in mind.

It does not need to be perfect.

It only needs to be reasonable enough to guide design decisions.
