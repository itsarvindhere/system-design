Usually, the interviewer gives a broad question like -

    1. Design YouTube
    2. Design Instagram
    3. Design a URL Shortener
    4. Design a Rate Limiter
    5. Design an Instagram Feed

At first, these questions look too big and that is normal.

The goal is not to design the perfect production system in 30 or 45 minutes. The goal is to show that you can break a vague problem into smaller parts, ask the right questions, make reasonable tradeoffs, and design a system that can scale.

In coding interviews, the problem is usually well defined like -

    Given an array, find the maximum subarray sum

But, in system design, the problem is open-ended.

For example -

    Design a notification system

This can mean many different things.

    Are notifications sent by email, SMS, push notifications, or in-app?
    Should it support millions of users?
    Should notifications be real-time?
    Can duplicate notification happen?
    Should users be able to mute notifications?
    Do we need retries?

So, before designing anything, we need to understand what exactly are we designing.

That is why system design interviews test communication as much as technical knowledge.

# THE DELIVERY FRAMEWORK

A good way to approach a system design interview is to follow a fixed structure. This is the Delivery Framework from Hello Interview (https://www.hellointerview.com/learn/system-design/in-a-hurry/delivery).

The main goal of the framework is to make sure that we deliver a working system. A fixed structure stops us from getting stuck and gives us something to fall back on when we feel overwhelmed.

    1. Requirements            (~5 minutes)
    2. Core Entities           (~2 minutes)
    3. API or System Interface (~5 minutes)
    4. Data Flow               (~5 minutes, optional)
    5. High-Level Design       (~10 to 15 minutes)
    6. Deep Dives              (~10 minutes)

The timings are for a 45 to 60 minute interview. We do not have to follow the order strictly, but this flow gives structure to our thinking. All the design problems in this section follow the same order.

Four ideas run through the whole framework -

    1. Keep requirements focused and quantified.
    2. Let the API drive the design.
    3. Start simple, then add complexity in the deep dives.
    4. Narrate our reasoning and let the interviewer steer when they want to.

## 1. REQUIREMENTS (~5 MINUTES)

The first step is to ask questions. Do not start with drawing boxes immediately.

For example, if the interviewer asks -

    Design a chat application

You can ask -

    1. Is this one to one chat or group chat?
    2. Should messages be real-time?
    3. Do we need read receipts?
    4. Do we need online/offline status?
    5. Should users be able to send images and videos?
    6. Do we need message history?
    7. Should messages be end-to-end encrypted?

These questions help reduce ambiguity.

There are usually two types of requirements =

    1. Functional Requirements
    2. Non-Functional Requirements

Functional requirements describe what the system should do. For a chat application functional requirements can be -

    Users can send messages
    Users can receive messages
    Users can create groups
    Users can see message history

Non-Functional requirements describe how well the system should work.

For example -

    Low Latency
    High availability
    Scalability
    Reliability
    Security
    Durability
    Fault Tolerance

A common mistake is jumping into database, caches, and queues too early.

First, understand the problem.

The framework adds a few rules on top of this -

    1. Functional requirements - keep the list to about the top 3 features. A long list hurts more than it helps. Phrase them as what users or clients should be able to do, and say clearly what is out of scope ("below the line").
    2. Non-functional requirements - pick the 3 to 5 most relevant ones and quantify them where possible. For example, "search results in under 500 ms" is better than "low latency".
    3. A useful checklist for non-functional requirements - CAP tradeoffs (consistency vs availability), environment constraints, scalability and traffic patterns, latency, durability, security, fault tolerance and compliance.
    4. Capacity estimation - skip the detailed math up front. Tell the interviewer that we will do calculations only when they affect a design decision.

### WHEN TO ESTIMATE THE SCALE

After requirements, estimate the scale. We do not need perfect numbers. Rough numbers are enough.

For example -

    10 Million daily active users
    Each user sends 20 messages per day
    Total messages per day = 200 million
    Average message size is 1 KB
    Storage per day is 200 GB

This gives us an idea of the system's size.

Scale affects design decisions. A system for 10,000 users may be simple but a system for 100 Million users needs a different architecture.

Some useful things to estimate are -

    1. Daily active users
    2. Requests per second
    3. Read/Write ratio
    4. Storage per day
    5. Bandwidth usage
    6. Peak traffic
    7. Data retention period

For example, if reads are much higher than writes, caching may become important. If writes are very high, sharding or partitioning may become important. If latency must be very low, we may need regional deployment, caching or websockets.

In the framework, estimation is not a separate step. We do it inside the deep dives, at the moment a number decides something. For example - does this data fit on one machine or does it need sharding? Is one database enough for the read traffic or do we need a cache? Is the number of open connections too high for one server?

See the note on Back of the Envelope Estimation for the formulas.

## 2. CORE ENTITIES (~2 MINUTES)

List the main entities as a rough first draft. These are the actors and the nouns that we need in order to satisfy the functional requirements. For a chat application, that can be -

    User, Conversation, Message

Choose clear names. Do not write the full data model yet, because we will discover more entities and fields as the design evolves. The fields are added later, next to each database in the high-level design.

## 3. API OR SYSTEM INTERFACE (~5 MINUTES)

The APIs show how the clients will interact with the system. For example, for a URL shortener -

    POST /short-urls
    GET /{shortcode}

For a chat app -

    POST /messages
    GET /conversations/{conversationId}/messages
    POST /conversations
    WebSocket /connect

API design does not need to be perfect, but it should show the main operations.

When designing APIs, think about -

    What request data is needed?
    What response is returned?
    Who is allowed to call this API?
    Is the operation idempotent?
    What errors can happen?

APIs help make the design concrete.

A few conventions from the framework -

    1. Default to REST. Consider GraphQL when clients have varied data needs, and RPC (like gRPC) for performance critical internal services.
    2. Design the core API first. Then add WebSockets or Server-Sent Events for real-time features.
    3. Use plural resource names, like /messages or /short-urls.
    4. The current user comes from the auth token. Never take it from a user_id in the request body or path.
    5. Map the endpoints to the functional requirements. The API drives the high-level design.

## 4. DATA FLOW (~5 MINUTES, OPTIONAL)

For systems that process data, list the sequence of actions that turns the input into the output. For example, for a video platform - upload, store the original, transcode, generate segments, publish.

Skip this step if the system does not have a meaningful sequence (for example a simple CRUD service). The list helps to inform the high-level design that follows.

## 5. HIGH-LEVEL DESIGN (~10 TO 15 MINUTES)

Now, we can draw the main components. For example -

        Client
            |
        Load Balancer
            |
        API Servers
            |
        Database

For a larger system, we may add Cache, Message Queue, Object storage, Search Index, Notification service, CDN, monitoring system.

The high-level design should be simple at first.

Start with the basic working system and then improve it.

Do not make the design complex too early.

The framework suggests -

    1. Build the design one API endpoint at a time, so that every functional requirement is covered.
    2. Talk through the request path from entry to response, and call out what state changes at each stage.
    3. Note the relevant fields next to each database. Skip obvious fields and do not worry about data types.
    4. If we spot a place for a cache or a queue, make a quick verbal and written note and move on. The added complexity is for the deep dives.

### DATA MODEL INSIDE THE HIGH-LEVEL DESIGN

Next, think about what data needs to be stored. For example, in a chat application, we may need -

    Users
    Conversations
    Messages
    Group Members
    Attachments

A simple messages table may look like -

    message_id
    conversation_id
    sender_id
    content
    created_at
    status

The data model depends on access patterns. For example -

    Get recent messages in a conversation
    Get all conversations for a user
    Search messages
    Mark messages as read

A good system design starts from queries and access patterns, not just entities.

## 6. DEEP DIVES (~10 MINUTES)

After the high-level design, the interviewer may ask you to go deeper.

For example -

    How will you scale the database?
    How will you handle retries?
    How will you prevent duplicate messages?
    How will you handle hot users?
    How will you recover from failure?
    How will you reduce latency?

This is where your fundamentals help. In this case, you may discuss -

    Caching
    Sharding
    Replication
    Load balancing
    Rate limiting
    Queues
    Consistent hashing
    Circuit breakers
    Idempotency
    Eventual consistency

The deep dive depends on the problem.

For a URL shortener, the deep dive may be short code generation and redirection latency.

For a chat app, the deep dive may be WebSockets, message ordering, and delivery guarantees.

For a news feed, the deep dive may be fan out, ranking, and caching.

Use this time to harden the design against the non-functional requirements. Address edge cases, find bottlenecks and improve the design in response to the interviewer's questions.

    - A junior candidate can expect the interviewer to point out the weaknesses.
    - A senior candidate should identify them and lead these discussions.
    - Leave room for the interviewer to ask questions. Talking over them hurts both the evaluation and the communication score.

### TRADEOFFS AND BOTTLENECKS

Every design has tradeoffs.

A good candidate does not pretend the design is perfect. For example -

    Caching improves latency but introduces cache invalidation problems.
    Sharding improves scalability but makes queries more complex.
    Replication improves read scalability but can cause replication lag.
    Strong consistency is safer but may reduce availability.
    Asynchronous processing improves performance but introduces eventual consistency.

Interviewers like when you can explain why you chose one approach over another.

System design is mostly about tradeoffs.

# COMMON MISTAKES

Some common mistakes in system design interviews are -

    1. Starting with technology before understanding requirements
    2. Not asking clarifying questions
    3. Ignoring scale
    4. Designing only the happy path
    5. Forgetting failure cases
    6. Not discussing tradeoffs
    7. Making the design too complex too early
    8. Not explaining your thinking clearly

For example, saying -

    "Use Kafka, Redis, Cassandra, Kubernetes, and microservices"

is not a good answer by itself.

The interviewer wants to know why each component is needed.

# A GOOD INTERVIEW FLOW

A good system design interview may sound like this -

    First, I want to clarify the requirements. I will keep the top three features and quantify the non-functional requirements.
    Then I will list the core entities.
    After that, I will define the API.
    Then I will create a high-level design, one endpoint at a time, and keep it simple.
    Finally, I will deep dive into the bottlenecks, failures and tradeoffs that matter for the non-functional requirements.

This tells the interviewer that we have a structured approach.

Before finishing a system design answer, check these points -

    Did I limit the functional requirements to the core, and say what is out of scope?
    Did I quantify 3 to 5 non-functional requirements?
    Did I only do estimation where it changed a design decision?
    Did I list the core entities?
    Did I define an API for each functional requirement?
    Did the high-level design cover every endpoint with a simple working flow?
    Did I note the fields next to each database?
    Did I lead the deep dives myself?
    Did I handle failures and scaling?
    Did I mention tradeoffs?
    Did I keep the design understandable and narrate my reasoning?

System design interviews are not about memorizing one perfect architecture. They are about thinking clearly.

A good design usually starts simple, then evolves based on scale, requirements, bottlenecks, and failure cases.
