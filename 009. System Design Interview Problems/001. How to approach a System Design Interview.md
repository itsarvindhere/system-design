Usually, the interviewer gives a broad question like -

    1. Design YouTube
    2. Design Instagram
    3. Design a URL Shortener
    4. Design a Rate Limiter
    5. Design an Instagram Feed

At first, these questions look too big and that is normal.

The goal is not to design the perfect production system in 30 or 45 minutes. The goal is to show that you can break a vague problem into smaller parts, ask the right questions, make reasonable tradeoffs, and design a system that can scale.

In coding interviews, the problem is usually well defined like -

    Given an array, find the maximum subarray sum

But, in system design, the problem is open-ended.

For example -

    Design a notification system

This can mean many different things.

    Are notifications sent by email, SMS, push notifications, or in-app?
    Should it support millions of users?
    Should notifications be real-time?
    Can duplicate notification happen?
    Should users be able to mute notifications?
    Do we need retries?

So, before designing anything, we need to understand what exactly are we designing.

That is why system design interviews test communication as much as technical knowledge.

# BASIC APPROACH

A good way to approach a system design interview is -

    1. Clarify the requirements
    2. Define the scale
    3. Design the APIs
    4. Design the data model
    5. Create a high-level architecture
    6. Deep dive into important components
    7. Discuss bottlenecks and tradeoffs

You do not always need to follow this order strictly, but this flow gives structure to your thinking.

## 1. CLARIFY REQUIREMENTS

The first step is to ask questions. Do not start with drawing boxes immediately.

For example, if the interviewer asks -

    Design a chat application

You can ask -

    1. Is this one to one chat or group chat?
    2. Should messages be real-time?
    3. Do we need read receipts?
    4. Do we need online/offline status?
    5. Should users be able to send images and videos?
    6. Do we need message history?
    7. Should messages be end-to-end encrypted?

These questions help reduce ambiguity.

There are usually two types of requirements =

    1. Functional Requirements
    2. Non-Functional Requirements

Functional requirements describe what the system should do. For a chat application functional requirements can be -

    Users can send messages
    Users can receive messages
    Users can create groups
    Users can see message history

Non-Functional requirements describe how well the system should work.

For example -

    Low Latency
    High availability
    Scalability
    Reliability
    Security
    Durability
    Fault Tolerance

A common mistake is jumping into database, caches, and queues too early.

First, understand the problem.

## 2. DEFINE THE SCALE

After requirements, estimate the scale. We do not need perfect numbers. Rough numbers are enough.

For example -

    10 Million daily active users
    Each user sends 20 messages per day
    Total messages per day = 200 million
    Average message size is 1 KB
    Storage per day is 200 GB

This gives us an idea of the system's size.

Scale affects design decisions. A system for 10,000 users may be simple but a system for 100 Million users needs a different architecture.

Some useful things to estimate are -

    1. Daily active users
    2. Requests per second
    3. Read/Write ratio
    4. Storage per day
    5. Bandwidth usage
    6. Peak traffic
    7. Data retention period

For example, if reads are much higher than writes, caching may become important. If writes are very high, sharding or partitioning may become important. If latency must be very low, we may need regional deployment, caching or websockets.

## 3. DESIGN THE APIs

The APIs show how the clients will interact with the system. For example, for a URL shortener -

    POST /short-urls
    GET /{shortcode}

For a chat app -

    POST /messages
    GET /conversations/{conversationId}/messages
    POST /conversations
    WebSocket /connect

API design does not need to be perfect, but it should show the main operations.

When designing APIs, think about -

    What request data is needed?
    What response is returned?
    Who is allowed to call this API?
    Is the operation idempotent?
    What errors can happen?

APIs help make the design concrete.

## 4. DESIGN THE DATA MODEL

Next, think about what data needs to be stored. For example, in a chat application, we may need -

    Users
    Conversations
    Messages
    Group Members
    Attachments

A simple messages table may look like -

    message_id
    conversation_id
    sender_id
    content
    created_at
    status

The data model depends on access patterns. For example -

    Get recent messages in a conversation
    Get all conversations for a user
    Search messages
    Mark messages as read

A good system design starts from queries and access patterns, not just entities.

## 5. CREATE A HIGH-LEVEL ARCHITECTURE

Now, we can draw the main components. For example -

        Client
            |
        Load Balancer
            |
        API Servers
            |
        Database

For a larger system, we may add Cache, Message Queue, Object storage, Search Index, Notification service, CDN, monitoring system.

The high-level design should be simple at first.

Start with the basic working system and then improve it.

Do not make the design complex too early.

## 6. DEEP DIVE INTO IMPORTANT COMPONENTS

After the high-level design, the interviewer may ask you to go deeper.

For example -

    How will you scale the database?
    How will you handle retries?
    How will you prevent duplicate messages?
    How will you handle hot users?
    How will you recover from failure?
    How will you reduce latency?

This is where your fundamentals help. In this case, you may discuss -

    Caching
    Sharding
    Replication
    Load balancing
    Rate limiting
    Queues
    Consistent hashing
    Circuit breakers
    Idempotency
    Eventual consistency

The deep dive depends on the problem.

For a URL shortener, the deep dive may be short code generation and redirection latency.

For a chat app, the deep dive may be WebSockets, message ordering, and delivery guarantees.

For a news feed, the deep dive may be fan out, ranking, and caching.

## 7. DISCUSS BOTTLENECKS AND TRADEOFFS

Every design has tradeoffs.

A good candidate does not pretend the design is perfect. For example -

    Caching improves latency but introduces cache invalidation problems.
    Sharding improves scalability but makes queries more complex.
    Replication improves read scalability but can cause replication lag.
    Strong consistency is safer but may reduce availability.
    Asynchronous processing improves performance but introduces eventual consistency.

Interviewers like when you can explain why you chose one approach over another.

System design is mostly about tradeoffs.

# COMMON MISTAKES

Some common mistakes in system design interviews are -

    1. Starting with technology before understanding requirements
    2. Not asking clarifying questions
    3. Ignoring scale
    4. Designing only the happy path
    5. Forgetting failure cases
    6. Not discussing tradeoffs
    7. Making the design too complex too early
    8. Not explaining your thinking clearly

For example, saying -

    "Use Kafka, Redis, Cassandra, Kubernetes, and microservices"

is not a good answer by itself.

The interviewer wants to know why each component is needed.

# A GOOD INTERVIEW FLOW

A good system design interview may sound like this -

    First, I want to clarify the requirements.
    Then I will estimate the scale.
    After that, I will define the APIs and data model.
    Then I will create a high-level design.
    Finally, I will discuss bottlenecks, failures, and tradeoffs.

This tells the interviewer that you have a structured approach.

Before finishing a system design answer, check these points -

    Did I clarify requirements?
    Did I estimate scale?
    Did I identify read/write patterns?
    Did I define APIs?
    Did I define the data model?
    Did I explain the main components?
    Did I handle failures?
    Did I discuss scaling?
    Did I mention tradeoffs?
    Did I keep the design understandable?

System design interviews are not about memorizing one perfect architecture. They are about thinking clearly.

A good design usually starts simple, then evolves based on scale, requirements, bottlenecks, and failure cases.
