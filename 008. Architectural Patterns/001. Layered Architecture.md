Layered Architecture is a way of organizing an application into separate layers, where each layer has a specific responsibility.

Instead of putting all the logic at one place, the system is divided into levels.

Each level focuses on one kind of work.

The basic idea is -

    Separate responsibilities into layers
    Keep each layer focused
    Let upper layers use lower layers

This is one of the most common and traditional architectural patterns in software systems.

It tries to answer the question -

    Which part of the application should be responsible for what?

We need layered architecture because as the applications grow, the code can become messy if everything is mixed together. For example -

    API handling
    Business rules
    Database queries
    Validation
    External service calls

If all of this is written together at one place, the code becomes hard to understand, test, and maintain.

Layered Architecture helps by giving structure. So, instead of one big block of logic, we split the application into clear sections. This makes the system easier to reason about.

# COMMON LAYERS

Different systems may name the layers differently. But, a very common structure is like this -

    1. Presentation Layer
    2. Application Layer
    3. Business or Domain Layer
    4. Data Access Layer
    5. Database or Infrastructure Layer

## 1. PRESENTATION LAYER

This is the layer that interacts with the outside world. For example -

    REST Controllers
    HTTP Handlers
    UI Endpoints
    GraphQL Resolvers

The job is usually to receive the requests, parse the input, return the responses, and handle protocol-level concerns.

This layer should usually not contain heavy business logic.

## 2. APPLICATION LAYER

This layer coordinates the user case or workflow of the application. For example -

    Place Order
    Register User
    Process Payment
    Generate Invoice

It tells the system what to do for a particular request. This layer often calls the domain logic and infrastructure services in the right orders.

The application layer is more about orchestration than deep business rules.

## 3. DOMAIN OR BUSINESS LAYER

This layer contains the core business rules of the system. For example -

    How order total is calculated
    Whether a refund is allowed
    When inventory can be reserved
    What conditions make a payment valid

This is often the most important layer because it contains the actual behavior of the business.

If the application changes business rules, this layer changes.

## 4. DATA ACCESS LAYER

This layer handles communication with the persistence systems. For example -

    Database queries
    ORM repositories
    Data mapping
    CRUD operations

The job is to read and write the data. This layer should ideally not contain business decision-making.

## 5. DATABASE OR INFRASTRUCTURE LAYER

This is the actual external system or technical dependency. For example -

    PostgreSQL
    MySQL
    Redis
    Kafka
    External APIs
    File storage

Some people keep this as part of the data layer, while others think of it separately.

The exact naming is less important than the responsibility split.

# HOW THE FLOW WORKS?

A typical request flow in a layered architecture is like this -

    1. Client sends the request
    2. Presentation Layer receives the request
    3. Application Layer handles the use case
    4 Domain Layer applies the business rules
    5. Data access layer reads or writes the data
    6. Response goes back upward

So, the flow usually moves downward for the work and upward for results.

Suppose, a user places an order.

The flow may look like this -

    Controller receives PlaceOrder request
    Application service starts PlaceOrder use case
    Domain logic checks order rules
    Repository saves order
    Response is returned to user

This is a normal example of layered architecture.

The main benefit is that each part has a clear job.

Separation of Concerns is the main idea in a layered architecture.

Presentation logic should not be mixed with database queries.

Database code should not contain HTTP concerns.

Business rules should not be scattered everywhere

Layered architecture helps keep these concerns apart.

This makes t he code cleaner.

# CLOSED LAYERS AND OPEN LAYERS

Sometimes the layered architecture is described using closed layers and open layers.

Closed layers mean each request must pass through the layer directly below it.

For example -

    Presentation -> Application -> Domain -> Data Access

There should be no skipping.

Open Layers mean some layers may be skipped if needed. For example -

    Presentation may directly call Application
    Application may directly use infrastructure helper

This can be practical, but too much skipping can weaken the architecture.

So, the idea is useful, but should be handled carefully.

# BENEFITS AND CHALLENGES

Some benefits of the layered architecture include -

    1. Clear structure
    2. Easy for teams to understand
    3. Easier unit testing
    4. Easier replacement of some technical parts
    5. Good maintainability for many applications
    6. Good fit for traditional enterprise applications

For example, if the database changes, much of the presentation or domain logic may stay unchanged.

This is one reason layers help.

Layered architecture also has some challenges like -

    1. Too much boilerplate
    2. Business logic may leak into wrong layers
    3. Can become rigid
    4. Performance may suffer if too many unnecessary layers are crossed
    5. In large systems, strict layering may become awkward
    6. Sometimes it leads to anemic domain models

For example, some projects create many thin layers that mostly pass data around without adding much value.

Then the architecture becomes formal but not very useful.

Anemic Domain Model means the domain layer becomes weak, while most business logic gets pushed into services or application code.

This is not always wrong, but it can make the model less expressive. So, layered architecture works best when responsibilities are kept meaningful.

Layered Architecture is a good fit when -

    1. Application is small or medium sized
    2. Domain complexity is manageable
    3. Team wants a familiar structure
    4. System is mostly request-response or CRUD style
    5. Clear separation is more important than advanced flexibility

For example -

    Internal business tools
    Admin dashboards
    Standard web backends
    Enterprise applications
    CRUD heavy systems

It may be less suitable when -

    1. Domain is very complex
    2. System needs strong modular boundaries
    3. Many integrations and external ports exist
    4. Event-driven or highly distributed behavior dominates
    5. You want business logic to be more isolated from frameworks

# LAYERED ARCHITECTURE VS MICROSERVICES

These are not opposites.

Layered architecture is a way to organize code inside an application.

Microservices is a way to split a whole system into separate services.

So, one microservice can internally use layered architecture.

For example -

    Order Service may itself have
        Presentation layer
        Application layer
        Domain layer
        Data access layer

So, the layered architecture is about the internal structure.
