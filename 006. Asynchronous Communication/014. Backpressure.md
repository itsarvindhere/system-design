# WHAT IS BACKPRESSURE?

Backpressure is a way for a slow part of the system to tell the fast part - "Slow down, I cannot keep up".

Think of a water pipe. If the pipe at the end is narrow, the water backs up. If we keep pouring in more water at the start, the pipe bursts. Backpressure is like closing the tap a little, so the water flow matches what the pipe can handle.

# THE PROBLEM

In an async system, a producer sends messages and a consumer processes them. What if the producer is faster?

    Producer -> 1000 messages per second
    Consumer -> 200 messages per second

Every second, 800 extra messages pile up in the queue. The queue grows and grows. Then -

    1. Memory or disk fills up
    2. Latency becomes huge (messages wait a long time)
    3. The system crashes or starts losing messages

Queues are good at handling short bursts. But they cannot fix a producer that is always faster than a consumer.

# SIGNS OF A PROBLEM

    1. Queue depth keeps growing
    2. Consumer lag keeps growing (in Kafka)
    3. Message age keeps growing
    4. Memory usage keeps going up

If the queue keeps growing and never goes down, we have a backpressure problem.

# WAYS TO HANDLE BACKPRESSURE

## 1. SLOW DOWN THE PRODUCER

The consumer or the queue tells the producer to slow down. For example, a bounded queue blocks the producer when it is full.

    Queue full -> producer has to wait

Or the API returns "429 Too Many Requests" or "503 Service Unavailable", so the client knows to try later.

## 2. USE A BOUNDED QUEUE

Never use an unlimited queue. Set a maximum size. When it is full, we have to decide what to do.

    Block the producer
    Reject the new message
    Drop the oldest or the least important message

An unbounded queue just hides the problem until the system runs out of memory.

## 3. DROP OR SAMPLE DATA

If some data is not very important, we can drop some of it.

For example - metrics, logs, or live location updates. If we miss one update, the next one will arrive soon anyway.

## 4. SCALE OUT THE CONSUMERS

Add more consumers so that the total processing speed goes up. In Kafka, this means more consumers in the group (up to the number of partitions).

But this works only if the work can be split. And if the real bottleneck is the database, adding more consumers can make things worse.

## 5. BATCHING

Process messages in batches instead of one by one. It reduces overhead and increases the throughput of each consumer.

## 6. RATE LIMITING

Limit how fast the producers can send. This protects the system at the entrance itself.

## 7. LOAD SHEDDING

When the system is overloaded, reject some requests on purpose, so that the rest can still be served well.

For example, reject low priority requests first and keep the important ones, like payments.

It is better to serve 80% of requests properly than to serve 100% of requests very slowly or crash.

# PUSH VS PULL

How the consumer gets messages also affects backpressure.

    Push model:
        The broker pushes messages to the consumer.
        The consumer can get overwhelmed if it is slow.
        So, we need a way for the consumer to say "stop".

    Pull model:
        The consumer asks for messages when it is ready.
        It takes only what it can handle.
        Backpressure is naturally built in.

Kafka uses the pull model. That is one reason why it handles slow consumers well. The messages just wait in the log until the consumer is ready.

# EXAMPLE

An app sends notifications.

    Producer -> Order Service creates notification events
    Queue    -> Notification Queue
    Consumer -> Email sending service

During a big sale, the Order Service creates 10x more events. The email provider is slow.

Without backpressure -

    The queue grows for hours. Emails are delayed a lot. Memory runs out.

With backpressure -

    1. Queue has a maximum size and an alert on queue depth
    2. More consumers are added automatically when the queue grows
    3. Low priority emails (promotions) are delayed or dropped
    4. Important emails (order confirmation, OTP) go first

# BEST PRACTICES

    1. Always use bounded queues
    2. Monitor queue depth and consumer lag
    3. Set alerts before the queue becomes full
    4. Decide what to do when overloaded (block, reject, or drop)
    5. Separate queues for important and unimportant work
    6. Auto scale consumers where possible
    7. Make consumers idempotent, because overloaded systems retry a lot

# SUMMARY

    Backpressure means the system tells producers to slow down when consumers cannot keep up.
    Without it, queues grow forever and the system fails.
    Use bounded queues, rate limiting, scaling, and load shedding to handle it.
    Pull based systems like Kafka have this naturally.
