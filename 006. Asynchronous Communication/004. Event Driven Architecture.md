Event Driven Architecture is a way of designing systems where services communicate by producing and reacting to events.

In this style, one service does something important and then emits an event to say that it happened. Other services that care about that event can react independently.

The basic idea is -

    A service performs an action
    It publishes an event
    Other services listen to that event
    Each service does its own work

For example, if a user places an order, the Order Service creates the order and then publishes this event -

    OrderCreated

Now, other services can react to it -

    Email Service sends confirmation
    Inventory Service reserves stock
    Analytics Service tracks the event
    Shipping Service starts shipment preparation
    Fraud Service runs checks

So, instead of order service directly calling each service, it simply publishes event and moves on.

This is the core idea of Event Driven Architecture.

# WHY DO WE NEED EVENT-DRIVEN ARCHITECTURE?

In many systems, one action affects many parts of the system.

For example, when the payment succeeds, we may need to do a lot of things like -

    Update order status
    Send receipt email
    Update analytics
    Trigger shipment workflow
    Notify the user
    Update loyalty points

If one service directly calls all three services, the system becomes tightly coupled. This can create problems like -


    - One service needs to know too many other services
    - Failures spread more easily
    - Adding new behavior becomes harder
    - Requests become slower
    - The system becomes harder to change

Event Driven Architecture helps solve this. Instead of one service controlling everything, each service reacts to events it cares about.

## EVENT

An event is a record of something that already happened in the system. For example -

    OrderCreated
    UserRegistered
    ProductAdded
    PaymentCompleted

Usually, we write an event in past tense because it represents a fact.

For example, 'OrderCreated' means the order has already been created.

We do not usually write -

    CreateOrder

Because this means "Do This". Instead, our event says -

    "This already happened"

This distinction is very important.

In Event Driven Architecture, services often publish events, and other services react to them.

## PRODUCER AND CONSUMER

A Producer is the service that creates and publishes the event. For example -

    Order Service publishes OrderCreated
    Payment Service publishes PaymentCompleted
    User Service publishes UserRegistered

The Consumer is the service that listens for the event and reacts to it. For example -

    Email Service listens to OrderCreated
    Analytics Service listens to OrderCreated
    Inventory Service listens to OrderCreated

The producer does not need to know exactly who all the consumers are. This is one of the biggest strengths of this architecture.

## BROKER OR EVENT BUS

Usually, events do not go directly from one service to another. Instead, they go through a broker or an event bus. For example -

    Order Service -> Event Bus -> Email Service
                               -> Inventory Service
                               -> Analytics Service

The broker receives events and delivers them to interested consumers.

Depending on the tool used, a Broker may also Store events, Retry delivery, Support fan-out, Track offsets, and Manage subscriptions. The exact behavior depends on the system being used.

# BENEFITS OF EVENT DRIVEN ARCHITECTURE

Some benefits are -

    1. Loose Coupling: Services do not need direct knowledge of each other.

    2. Better Scalability: Consumers can scale independently. If analytics traffic grows, we can scale the Analytics Service without scaling the Order Service.

    3. Easier Extension: New Services can be added later. For example, if we later add a Recommendation Service, it can simply subscribe to existing events.

    4. Better Fault Isolation - One failure does not always break the whole flow immediately. For example, if analytics is down, the order may still be created successfully.

    5. Faster user-facing requests - It means follow-up work can happen later in the background instead of inside the request.

# CHALLENGES OF EVENT DRIVEN ARCHITECTURE

The Event Driven Architecture also adds complexity. Here are some common challenges -

    1. Harder debugging: It happens because the flow is spread across many services. Instead of one request and one response, there may be many downstream reactions.

    2. Duplicate events: They can happen in real systems, so consumers usually need Idempotency.

    3. Event Ordering Issues - Ordering can be tricky because events may not always arrive or be processed in the exact order people expect.

    4. Eventual Consistency - This is common because one service may update immediately while others update later. For example, the order may be visible instantly, but analytics and notification updates may happen after some delay.

    5. Event schema changes can break consumers

# WHEN TO USE AND WHEN NOT TO USE EVENT DRIVEN ARCHITECTURE

Use Event Driven Architecture when -

    1. One action should trigger multiple downstream actions
    2. You want services to be loosely coupled
    3. You want independent scaling of consumers
    4. You want asynchronous processing
    5. You want to add new consumers later without changing the producer

For example -

    1. Order systems
    2. Payment workflows
    3. Notification systems
    4. Analytics pipelines
    5. User activity tracking
    6. Inventory updates
    7. Audit logs

Do not use Event Driven Architecture everywhere. Avoid it when -

    1. You need an immediate synchronous response
    2. The flow is very simple and direct API calls are enough
    3. Strong consistency is required at every step
    4. The team is not ready for the operational complexity
    5. Debugging and tracing would become too difficult for the use case

For example, login verification or checking current account balance is usually better as direct synchronous communication.

Event Driven Architecture is not a replacement for every API call.

Remember that Event Driven Architecture does not remove work. It only changes how the work is coordinated. If one event triggers ten downstream actions, those ten actions still need to happen. The architecture simply makes the system more decoupled and flexible.

Also, Events should represent facts, consumers should be idempotent, and systems should be designed for eventual consistency in the Event-Driven systems.
