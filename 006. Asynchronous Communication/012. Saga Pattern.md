Saga Pattern is a way to manage a business workflow that spans multiple services without using one large distributed transaction.

In Distributed Transactions, the goal is usually -

    All steps succeed together
    OR
    All steps fail together

That sounds ideal, but in distributed systems it becomes expensive and difficult because there are multiple services, multiple databases, network failures, timeouts, and partial failures.

That is why many modern distributed systems avoid one large cross-service transaction.

Instead, they often use the Saga Pattern.

The basic idea is -

    1. Break one business workflow into smaller local transactions
    2. Let each service complete its own step
    3. If one later step fails, undo earlier completed business effects using compensating actions

So, Saga Pattern is a practical alternative to distributed transactions for many multi-service workflows.

For example, placing an order may require -

    1. Create order
    2. Reserve inventory
    3. Charge payment
    4. Start shipping
    5. Send confirmation

If all this happens inside one service and one database transaction, rollback is simple.

But in microservices, these steps often happen in different services with different databases.

Now imagine this happens -

    Order created successfully
    Inventory reserved successfully
    Payment failed

What should happen now?

We usually do not want the system to keep the order and inventory reservation as if everything succeeded.

So, instead of one global rollback, the system often uses compensating actions like -

    Cancel the order
    Release inventory

This is the main idea of Saga Pattern.

# LOCAL TRANSACTION

In a Saga Pattern, each step is usually a Local Transaction performed by one service.

For example -

    Order Service creates the order
    Inventory Service reserves the stock
    Payment Service charges customer

Each service updates its own data store independently.

This is important. A Saga is not one giant database transaction. It is a sequence of smaller local transactions.

# COMPENSATING TRANSACTION

A compensating transaction is an action that tries to undo the business effect of an earlier successful step.

For example -

    Reserve inventory
    Later payment fails
    Compensating action: release inventory

OR

    Charge payment
    Later shipment creation fails
    Compensating action: refund the payment

This is not always a perfect technical rollback in the database sense. It is usually a business rollback.

This is an important distinction. For example, if an email was already sent, you cannot "unsend" it. But you can send a follow-up correction email.

So, compensation means -

    Undo the business effect as much as possible

For example, if the flow is -

    1. Order Service creates order with status PENDING
    2. Inventory Service reserves stock
    3. Payment Service charges customer
    4. Shipping Service creates shipment
    5. Order Service marks order CONFIRMED

And step 3 fails.

Then, the Saga may do compensation as -

    Payment failed
    Inventory Service releases reserved stock
    Order Service marks the order as CANCELLED

So, instead of one database rollback, the system performs business-level undo steps.

This is the core idea of Saga Pattern.

# DISTRIBUTED TRANSACTIONS VS SAGA PATTERN

Distributed Transactions try to achieve one atomic outcome across multiple participants.

So, the goal is -

    All succeed together
    OR
    All fail together

Saga Pattern works differently.

It says -

    Let each service commit its own local transaction
    Coordinate the workflow step by step
    If something fails later, run compensating actions

So -

    Distributed Transaction = atomic commit across services
    Saga Pattern = local commits with compensation

This is the key contrast.

# CHOREOGRAPHY AND ORCHESTRATION

There are two common ways to implement a Saga.

## 1. CHOREOGRAPHY

In Choreography, services react to events and decide their own next actions. There is no central controller.

For example -

    Order Service publishes OrderCreated
    Inventory Service listens and reserves stock
    Inventory Service publishes InventoryReserved
    Payment Service listens and charges payment
    Payment Service publishes PaymentSucceeded
    Shipping Service listens and creates shipment

If a failure happens, a service may publish a failure event and other services react with compensating actions. For example -

    PaymentFailed event published
    Inventory Service releases stock
    Order Service marks order cancelled

So, Choreography is event-driven. The services coordinate by emitting and reacting to events.

The benefits include -

    1. Loose coupling
    2. Natural fit for event-driven systems
    3. No central coordinator
    4. Easy to extend in some cases

But, there are also challenges like -

    1. Flow becomes hard to see
    2. Debugging is harder
    3. Logic becomes scattered across services
    4. Adding new steps may make the flow messy
    5. Failure handling can become complicated

In small systems, choreography may work well. But in large workflows, it can become hard to reason about.

## 2. ORCHESTRATION

In Orchestration, there is one central component called the 'Orchestrator' that controls the flow.

The Orchestrator tells each service what to do next.

For example -

    Orchestrator tells Order Service: create order
    Orchestrator tells Inventory Service: reserve stock
    Orchestrator tells Payment Service: charge payment
    Orchestrator tells Shipping Service: create shipment

If one step fails, the orchestrator triggers compensating actions. For example -

    Payment step fails
    Orchestrator tells Inventory Service: release stock
    Orchestrator tells Order Service: cancel order

So, orchestration is more centralized.

The benefits are -

    1. Flow is easier to understand
    2. Failure handling is more explicit
    3. Easier to monitor one business workflow
    4. Easier to manage complex multi-step processes

But, there are also some challenges like -

    1. Central coordinator adds dependency
    2. Orchestrator can become complex
    3. More control is concentrated in one place

So, both styles have tradeoffs.

The easiest way to think about them is - 

    Choreography:
        Services react to events
        No central brain

    Orchestration:
        One coordinator drives the workflow
        Central brain exists

So, Choreography spreads control while Orchestration centralizes control.

# WHEN SAGA PATTERN IS USEFUL?

It is useful when -

    1. One business workflow spans multiple services
    2. Each service owns its own database
    3. Distributed transactions are impractical
    4. Business rollback is needed when a later step fails
    5. Eventual consistency is acceptable

Some common examples are -

    1. Order processing
    2. Travel booking
    3. Payment workflows
    4. Inventory reservation
    5. Subscription activation
    6. Refund processing

Saga Pattern is closely related to Eventual Consistency. This is because the full workflow does not become complete in one atomic moment.

Instead -

    One local step succeeds
    Another local step succeeds later
    If a failure happens, compensating actions happen later

So, for some time, the system may be in an intermediate state.

For example -

    Order is PENDING
    Inventory is reserved
    Payment is still processing

This is normal in saga-based workflows.

Eventually, the workflow should reach a final state like -

    CONFIRMED
    CANCELLED

This is why Saga-based systems often rely on Eventual Consistency.

# IMPORTANT DESIGN IDEAS

When designing Sagas, some ideas are very important.

## 1. IDEMPOTENCY

Steps and compensating actions should usually be idempotent. If the same command or event is retried, the system should not produce incorrect or duplicate effects.

## 2. STATE TRACKING

The workflow state should be visible. For example -

    PENDING
    RESERVED
    PAID
    CONFIRMED
    FAILED
    CANCELLED

This helps with monitoring and recovery.

## 3. TIMEOUTS

Sometimes one step may never respond. So, Sagas often use timeouts. For example -

    Wait for payment confirmation for 10 minutes
    If not received, release stock and cancel order

## 4. RETRIES

Temporary failures may be retried before compensation is triggered.

## 5. OBSERVABILITY

Since the flow crosses many services, tracing and correlation IDs are very important.

# LIMITATIONS OF SAGA PATTERN

Saga Pattern is useful but it has limitations like -

    1. More business complexity
    2. Harder failure handling
    3. Compensation is not always perfect
    4. Some actions cannot be fully undone
    5. Debugging distributed workflows is harder
    6. Temporary inconsistent states are common

For example, sending an email or SMS is hard to truly roll back. So, not every action has a clean compensating transaction.

# ONE IMPORTANT THING TO REMEMBER

Saga Pattern does not give one single atomic transaction across all services.

Instead, it gives a structured way to manage distributed business workflows and recover from partial failure.

So, the mental model is -

    One large distributed transaction is hard
    So we use local transactions step by step
    If a later step fails
    We undo earlier business effects using compensation

In one line, Saga Pattern means -

    A way to manage a distributed multi-step workflow by using local transactions for each step and compensating actions when part of the workflow fails.
