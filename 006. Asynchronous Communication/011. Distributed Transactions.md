Distributed Transactions are transactions that span multiple systems, services, or databases and try to ensure that all parts either succeed together or fail together.

In a normal single transaction, the idea is simple -

    All changes happen together
    OR
    None of them happen

For example -

    Deduct money from Account A
    Add money to Account B

If something fails in between, the database rolls everything back.

This works well when everything is inside one database system. But, in distributed systems, one business action usually touches multiple services.

For example -

    Order Service creates the order
    Payment Service charges the customer
    Inventory Service reserves the stock

So, the question now becomes -

    How do we make sure all these steps succeed together?

That is the main problem of distributed transactions.

We need Distributed Transactions when one business operation changes data in more than one place, but the final outcome should still be consistent.

Taking the order example, if payment succeeds but inventory reservation fails, the system may end up in a bad state. For example -

    Customer charged
    But no inventory reserved
    Or order not confirmed

So, systems need some way to coordinate multiple updates across multiple services.

This is where Distributed Transactions come in.

# WHAT MAKES DISTRIBUTED TRANSACTIONS HARD?

Distributed Transactions are hard because distributed systems have many failure points. Some common problems are -

    1. Network failures
    2. Service crashes
    3. Timeouts
    4. Partial completion
    5. Retries
    6. Uncertain state
    7. Slow coordination

For example -

    Order Service says 'I created the order'
    Payment Service says 'I charged the customer'
    Inventory Service times out

Now, what is the 'true' final state?

This is difficult because some parts may have succeeded while others did not.

This is called a Partial Failure, and it is one of the biggest problems in Distributed Systems It means one part of the distributed operation succeeds while other fails.

For example -

    Payment succeeds
    Inventory reservation fails
    Order update fails

Now, the business flow is incomplete.

This is the major reason distributed transactions are difficult. In one database, rollback is usually straightforward. Across many services, rollback is much harder because each service may already have committed its local changes.

So, once partial success happens, the system needs co-ordination or compensation.

# ATOMICITY IN DISTRIBUTED SYSTEMS

A transaction usually tries to provide atomicity.

Atomicity means Either everything happens or Nothing happens.

In Distributed Transaction, atomicity becomes much harder because each service controls its own local state.

For example -

    Payment database commits
    Inventory database has not committed yet
    Network fails

Now, we do not know whether the overall transaction should be considered successful or failed.

So, distributed atomicity requires extra coordination.

All participants needs to agree upon whether to commit or abort. For example -

    Coordinator asks each participant if it can commit
    Participants reply
    Coordinator decides final outcome
    Participants follow that decision

This sounds reasonable, but it becomes difficult when failures happen in the middle.

For example -

    Coordinator crashes
    Network breaks
    Participant waits forever
    One participant commits but another does not hear the decision

This is why distributed transactions are not simple.

# TWO PHASE COMMIT

One of the most common ideas associated with distributed transactions is a Two Phase Commit, often called a '2PC'.

It is a coordination protocol used to try to make multiple systems commit or abort together.

The idea is -

    Phase 1: Prepare phase
    Phase 2: Commit phase

In the prepare phase -

    Coordinator asks all participants:
        "Can you commit?"

Each participant does its checks and replies -

    Yes, I am ready.

    OR

    No, I cannot commit.

If all participants agree, the coordinator moves to commit phase. Then it tells everyone -

    Commit now

If any participant says No, then the coordinator tells everyone -

    Abort

So, at high level -

    First ask for readiness
    Then decide commit or abort

This is the classic distributed transaction model.

But, the Two Phase Commit also introduces problems like -

    1. It can block
    2. It adds latency
    3. It needs a coordinator
    4. It reduces availability
    5. It becomes painful during failures
    6. It does not scale well in modern systems

For example, if the coordinator crashes at the wrong time, some participants may be stuck waiting. They may hold locks and wait for the final decision.

This blocking behavior is one of the biggest problems.

Distributed transactions usually increase latency. That is because the system now needs extra round trips and coordination before the operation can finish.

It also reduces performance because services may need to hold locks or reserved state longer while waiting for others.

Distributed transactions often trade availability for stronger consistency. If one participant is unavailable, the whole transaction may need to wait or fail.

This can be the correct choice in some systems, but it also reduces availability. In highly distributed systems, this tradeoff becomes expensive.

# WHY MICROSERVICES MAKE DISTRIBUTED TRANSACTIONS HARDER?

That's because each service usually owns its own database and controls its own data independently.

This is actually one of the reasons microservices exist. But, it creates a challenge.

For example -

    Order Service owns orders
    Payment Service owns payments
    Inventory Service owns stock

No service should directly control another service's database.

So, one global transaction across all of them becomes awkward and tightly coupled.

This is why many microservices systems avoid distributed transactions unless absolutely necessary.

# WHEN DISTRIBUTED TRANSACTIONS ARE NECESSARY AND WHEN THEY ARE NOT?

They are useful in some cases like when -

    1. Strong consistency is absolutely required
    2. The number of participants is small
    3. The systems are tightly controlled
    4. The performance cost is acceptable
    5. The tech stack supports it well

Some examples include enterprise systems, financial workflows or controlled internal platforms where correctness requirements are extremely strict.

So, distributed transactions are not always bad. They are just expensive and complex.

They are often a bad fit when -

    1. The system is highly distributed
    2. High availability is important
    3. The workflow is long-running
    4. Services are loosely coupled
    5. Temporary inconsistency is acceptable
    6. The business flow can tolerate compensation instead of instant atomic commit

In these cases, alternatives are often better. Because distributed transactions are hard, modern systems often use other patterns instead. Some common alternatives include -

    1. SAGA Pattern
    2. Event-driven workflows
    3. Outbox pattern
    4. Idempotent retries
    5. Compensation logic
    6. Eventual Consistency
