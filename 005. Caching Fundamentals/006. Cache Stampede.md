Cache Stampede is a problem that happens when many requests try to rebuild the same cache data at the same time.

As we know, the Cache stores frequently used data so that every request does not have to go to the database.

So, the flow is -

    1. Request comes in
    2. App checks cache
    3. If cache hit, return data
    4. If cache miss, fetch from database
    5. Store result in cache
    6. Return result

This works fine when only a few requests miss the cache. But, let's say a very popular cache key expires.

For example -

    homepage:popular_products

This key is requested by thousands of users.

Now, if this cache entry expires at the same time for everyone, then many requests will get a cache miss together. So, instead of one request going to the database and rebuilding the cache, thousands of requests may go to the database at the same time.

This sudden load can overload the database or the backend service. And this problem is called the Cache Stampede.

So, this problem usually happens when a hot key expires. A hot key means a cache key that receives a lot of traffic. For example, Homepage data, Trending posts, Popular product details, Search results for popular keywords, User feed for a celebrity account and so on.

So, the main issue is -

    Many requests try to do the same expensive work at the same time.

# CACHE STAMPEDE VS CACHE MISS

A Cache miss is normal. It simply means that the requested data was not found in the cache.

Cache Stampede is different. In Cache Stampede, many requests miss the same cache key at the same time.

    Cache miss:
        One or few requests go to database

    Cache stampede:
        Many requests go to database together for the same data

So, a cache miss is expected while the a cache stampede happens when valid cached data expires and many requests try to rebuild it together.

# PREVENTING CACHE STAMPEDE

There are some ways in which we can prevent this problem.

## 1. LOCKING

The idea is simple -

    Only one request should rebuild the cache.
    Other requests should wait or use the old data.

For example, let's say that the homepage cache expires. The first request gets a cache miss and so, it takes the lock -

    lock:homepage:data

Then, it fetches data from the database and rebuilds the cache.

Other requests see that teh lock already exists, so they do not hit the database.

The flow is -

    1. Request comes in
    2. Cache miss
    3. Try to acquire lock
    4. If lock acquired, fetch from database and update cache
    5. If lock not acquired, wait or return stale data

This prevents thousands of requests from hitting the database. Only one request does the expensive work.

The downside is that locking adds complexity. We also need to ensure that the lock has a timeout otherwise if the request holding the lock fails, the lock may stay forever.

So, locks should always have expiry.

## 2. SERVE STALE DATA WHILE REFRESHING

Another good strategy is that we serve stale data for a short time while refreshing the cache in the background. The idea is -

    If cached data is slightly old, still return it.
    Then refresh it asynchronously.

For example -

    Cache data expired 2 seconds ago
    Instead of sending all users to database
    Return old cache value
    One background job refreshes it

This is useful when a little staleness is acceptable. For example, homepage data, trending posts, product recommendations, news feed ranking, analytics dashboard, etc.

The benefit is that users still get fast responses and the database is also protected. But, the downside is that users may see old data for a short time.

But, for many systems, this is better than overloading the database.

## 3. RANDOMIZED TTL

If many cache keys are created at the same time with the same TTL, they may also expire at the same time. For example -

    product:1 -> TTL 10 minutes
    product:2 -> TTL 10 minutes
    product:3 -> TTL 10 minutes
    product:4 -> TTL 10 minutes

If these keys were created together, they may also expire together.

This can create a sudden spike. To avoid this, we can add randomness to the TTL. For example -

    product:1 -> TTL 9 minutes 40 seconds
    product:2 -> TTL 10 minutes 20 seconds
    product:3 -> TTL 11 minutes
    product:4 -> TTL 9 minutes 10 seconds

Now, all keys do not expire at the exact same time.

This spreads the load over time and it is called TTL jitter.

The idea is -

    Do not let many cache keys expire together.

It is very easy to implement and very useful.

## 4. REFRESH AHEAD

In this, the system refreshes the cache before it expires. For example, let's say that the homepage data has a TTL of 10 minutes. Instead of waiting for 10 minutes to expire, the system may refresh it at 9 minutes. The flow is -

    1. Cache entry is close to expiry
    2. Background process refreshes it
    3. Users continue getting cache hits

This is useful for hot keys like Homepage data, trending posts, popular products, leaderboards and more.

Refresh-ahead reduces the chance that the users will hit an expired cache key. The downside is that we may refresh data that no one needs anymore. So, refresh-ahead is best for data that is predictably popular.

## 4. BACKGROUND CACHE WARMING

Cache warming means loading important data into cache before the users request it. For example, after a deployment or a cache restart, the cache may be empty. If the traffic comes immediately, many requests may hit the database.

To avoid this, we can pre-load important keys.

For example -

    1. Load homepage data
    2. Load top products
    3. Load popular categories
    4. Load common configuration

This helps to prevent sudden load after cache restart or deployment.

Cache warming is useful when we already know which data is important. The downside is that it requires extra logic and may load data that is not actually needed.

# WHEN IS CACHE STAMPEDE MOST DANGEROUS?

Cache Stampede is the most dangerous when -

    1. The cache key is very popular
    2. The backend operation is expensive
    3. Many users request the key at the same time
    4. The database is already under high load
    5. Retries are enabled without limits
    6. Many cache keys expire together

For example, homepage data during peak traffic is risky.

A popular product during a sale is risky.

A leaderboard during a live event is risky.

A cache restart during high traffic is risky.

In these cases, we should design cache refresh carefully.

# BEST PRACTICES

Some good practices to avoid cache stampede are -

    1. Use locks for hot keys
    2. Use lock timeout
    3. Serve stale data while refreshing
    4. Add random jitter to TTL
    5. Use refresh-ahead for popular keys
    6. Warm important cache keys after deployment or restart
    7. Avoid making many keys expire at the same time
    8. Monitor cache miss spikes
    9. Monitor database load after cache expiry
    10. Use rate limits or backoff for retries

A practical approach is -

    TTL + Random Jitter + Locking + Serve Stale Data

This means -

    1. Cache data with TTL
    2. Add randomness so keys do not expire together
    3. Allow only one request to rebuild hot cache data
    4. Let other requests use old data briefly if acceptable
