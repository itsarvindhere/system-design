Cache Eviction policies decide which data should be removed from the cache when the cache becomes full.

As we know, a Cache has a limited memory. This means, we cannot store things in a Cache forever. So, when a new data needs to be added and the cache is already full, the system needs to decide which existing items must be removed.

And this decision is called 'Cache Eviction.'

For example, suppose we are caching the product details in an e-commerce application. The cache can only store 3 products. So, currently it has -

    Product A
    Product B
    Product C

Now, a request comes for Product D. the system fetches it from the database and wants to store it in the cache.

But, the cache is full.

So, one existing product needs to be removed and the cache eviction policy is the one that decides whether to remove Product A or B or C.

# CACHE EVICTION POLICIES

## 1. LEAST RECENTLY USED (LRU)

In LRU, the cache removes the item that was not used for the longest time.

The idea is simple -

    If something has not been used recently, it is less likely to be used again soon.

For example, if the cache has -

    A
    B
    C

And the recent access order is -

    A was used 10 minutes ago
    B was used 2 minutes ago
    C was used 5 seconds ago

Now, if we want to remove one item, LRU will remove 'A' because 'A' is the least recently used item.

LRU is very common because in many systems, recently used data is likely to be used again. Some example are User session data, Product details, Profile data, and Recently viewed items.

If a user recently opened a product page, there is a decent chance they may refresh it, share it, or open related pages.

So keeping recently accessed data in cache often works well.

## 2. LEAST FREQUENTLY USED (LFU)

In LFU, the cache removes the item that has been used the least number of times. The idea is -

    If something is rarely used, it is less valuable to keep in cache.

Taking the same example of 'A', 'B', and 'C' in the cache, suppose we have -

    A accessed 100 times
    B accessed 5 times
    C accessed 2 times

Now, if we need to remove one item, LFU will remove C since it is the least frequently used item.

LFU is useful when some data is consistently popular. For example - Popular products, Trending posts, Frequently accessed configuration, Common search results etc.

But, it has a problem.

Suppose one item was very popular yesterday but no one used it today.

It may still have a high frequency count, so LFU will keep it in the cache even though it ios no longer useful. To handle it, real systems, use LFU with aging, where old frequency counts slowly lose importance over time.

## 3. First In, First Out (FIFO)

In FIFO, the cache removes the item that entered the cache first.

The idea is simple -

    Oldest inserted item is removed first.

So, if the items entered in this order -

    A -> B -> C

Now, if 'D' has to be added and the cache is full, FIFO removes 'A'.

FIFO is simple to implement but it does not consider whether an item is frequently used or recently used. This means, even if 'A' is very popular, FIFO still removes it because it entered first.

So, it is simple to implement but not always the most efficient.

## 4. Last In, First Out (LIFO)

In LIFO, the cache removes the item that was most recently added. So, the idea is -

    Newest inserted item is removed first.

For example, if items entered in cache in this order -

    A -> B -> C

If the cache needs space, LIFO removes C.

LIFO is not very common for general caching. This is because recently added data may be useful soon, and removing it immediately may not be a good idea.

But, it can be useful in some special cases where the newest data is temporary or less important.

## 5. RANDOM REPLACEMENT

In Random Replacement, the cache randomly removes any item. So, if the cache has -

    A
    B
    C

When D needs to be added, the cache may randomly remove either A or B or C.

The policy is very simple and has a low overhead.

It does not need to track access time or frequency. But, since it is random, it may remove important or frequently used data.

Random replacement can sometimes work surprisingly okay in large systems. But, it is usually not the first choice when we care about cache hit ratio.

## 6. TTL-BASED EVICTION

TTL means Time To Live.

In TTL-based eviction, each cache entry is stored only for a fixed amount of time. For example -

    Product details -> cache for 10 minutes
    User session -> cache for 30 minutes
    OTP -> cache for 5 minutes

After th TTL expires, the item is removed or treated as invalid.

    SET product:55 value EX 600

This means product 55 is cached for 600 seconds. TTL is useful when data should not stay cached forever. For example Prices, Inventory, Auth Tokens, OTPs, API responses, temporary user data and more.

TTL helps reduce stale data. But, it alone does not always solve memory pressure.

If many items are added before their TTL expires, the cache can still become full. So, TTL is often used along with other eviction policies like LRU or LFU.

## 7. MOST RECENTLY USED (MRU)

In MRU, the cache removes the item that was the most recently used.

Yes, it sounds strange at first because why would we remove the item that was most recently used?

But, MRU is useful in some special cases where recently used data is unlikely to be used again. For example, suppose a system is scanning through a large dataset sequentially -

    A -> B -> C -> D -> E -> F

If each item is accessed once and probably not needed again soon, keeping the most recently used item may not help.

So MRU can be useful in specific workloads, but it is not as commonly used as LRU.

# LRU vs LFU

The simple difference is that LRU cares about recency -

    When was this item last used?

While LFU cares about frequency -

    How many times has this item been used?

So, if we have three items -

    A used 100 times, but last used yesterday
    B used 5 times, but last used 1 minute ago
    C used 2 times, but last used 5 seconds ago

LRU may remove item A because it was not used recently.
LFU may remove item C because C has the lowest usage count.

So, the best policy depends on the access pattern.

If recent usage predicts future usage, LRU works well.
If long-term popularity predicts future usage, LFU works well.

# CACHE EVICTION vs CACHE EXPIRATION

They are related, but not the same. Cache expiration usually happens because time is over -

    This item had a TTL of 10 minutes.
    10 minutes passed.
    So the item is expired.

Cache eviction usually happens because the cache needs space -

    Cache is full.
    New item needs to be added.
    So one existing item must be removed.

So, simply put -

    Expiration removes old data based on time
    Eviction removes data based on memory pressure

In real systems, both can happen together.

# CACHE HIT RATIO

Cache Hit Ratio tells us how often requests are served from the Cache.

For example, if we get 100 requests and 80 are served from the cache then the Cache Hit Ratio is 80%.

A good Cache Eviction policy should improve the cache hit ratio. If the cache keeps removing the useful data, the cache misses will increase. More cache misses means more requests will go to the database or backend services and this can increase latency and load.

So, Cache eviction policy directly affects performance.

# WHICH POLICY TO USE?

Well, there is no single best eviction policy for every system. It depends on the access pattern.

For general-purpose caching, LRU is very common.

If some items are consistently popular, LFU may work better.

If data must expire after a fixed time, use TTL. If the cache stores temporary data like OTPs or Tokens, TTL is very important.

For example, in Redis, a common practical choice is -

    allkeys-lru

This means Redis will evict the least recently used keys when memory is full.

For workloads with strong popularity patterns, we may choose -

    allkeys-lfu

But we should not just guess. In production, we should monitor -

    1. Cache hit ratio
    2. Memory usage
    3. Evicted keys
    4. Latency
    5. Database load
    6. Hot keys

The best eviction policy is the one that works well for the actual traffic pattern.
