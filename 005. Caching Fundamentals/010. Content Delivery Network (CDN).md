CDN stands for Content Delivery Network.

A CDN is a network of servers distributed across different geographic locations.

The idea is simple -

    Store content closer to users, so it can be delivered faster.

For example, suppose your main server is in India. Now, if a user from the USA requests an image from your website, the request may have to travel all the way to India.

This can increase latency.

But, if the same image is cached in a CDN server in the USA, then the user can download it from that nearby CDN server instead of going to the server in India.

So, CDN helps reduce latency by serving content from a location closer to the user.

So, with a CDN, the flow can be -

    First user:
        User -> CDN
        CDN does not have logo.png
        CDN fetches logo.png from origin server
        CDN stores logo.png
        CDN returns logo.png to user

    Second user:
        User -> CDN
        CDN already has logo.png
        CDN returns logo.png directly

So, after the first request, future users can get the image from CDN. This reduces load on the origin server.

# ORIGIN SERVER

The origin server is the main server that owns the original content. For example, if we upload the images to our backend or object storage, that is the origin.

The CDN does not usually create the original data. It only keeps the cached copies of it.

If the CDN does not have the files, it asks the origin server. So, origin is the source of truth. CDN is a fast delivery layer.

# EDGE SERVER

An edge server is a CDN server that is located close to the users. CDN providers have many edge servers around the world. For example -

    Edge server in India
    Edge server in Singapore
    Edge server in Europe
    Edge server in USA

When a user requests content, the CDN tries to route the user to a nearby edge server. For example -

    User in Delhi -> CDN edge in India
    User in London -> CDN edge in Europe
    User in New York -> CDN edge in USA

This reduces the physical distance the data has to travel.

Less distance usually means lower latency.

# WHAT CAN BE SERVED THROUGH CDN?

CDNs are commonly used for static content like Images, Videos, CSS Files, JS files, Fonts, Documents, and Software Downloads. These files are good CDN candidates because they are often read many times and do not change very frequently.

CDNs can also cache some dynamic content.

For example, public product pages, news articles, blog pages, public API responses, search pages with common queries.

But, the dynamic content needs careful cache rules.

For user-specific data, we must be very careful. For example, For example, we should not accidentally cache one user's private dashboard and serve it to another user.

# CDN AND TTL

CDN also uses TTL or Time To Live.

It decides how long content can stay cached at the CDN edge. For example -

    logo.png -> cache for 30 days
    product page -> cache for 5 minutes
    API response -> cache for 30 seconds

If the TTL has not expired, CDN can serve the cached content.

If the TTL expires, CDN may revalidate or fetch a fresh copy from origin.

For static assets like CSS, JavaScript, images, and fonts, we often use long TTL. For dynamic content, we usually use shorter TTL.

# CACHE CONTROL HEADERS

CDN caching is often controlled by HTTP headers. One important header is -

    Cache-Control

For example -

    Cache-Control: public, max-age=3600

This means, the response can be cached publicly for 3600 seconds.

Another example is -

    Cache-Control: no-store

This means, the response should not be stored in the cache. This is useful for sensitive data like bank account page, payment details, private user dashboard and more.

Here are some common cache control values -

    public:
        Response can be stored by shared caches like CDN

    private:
        Response is meant for one user and should not be stored by shared caches

    max-age:
        How long the response can be cached

    no-cache:
        Cache must revalidate before using

    no-store:
        Do not store the response at all

So, cache headers are very important for CDN behavior.

# CDN INVALIDATION

Sometimes, we need to remove content from the CDN before its TTL expires. This is called CDN invalidation or CDN purge.

For example, let's say we cached product image with a TTL of 30 days.

Now, the image is wrong and we need to replace it immediately.

If we do nothing, the users will keep seeing the old image until the TTL expires. So, we can purge the CDN cache.

After that, the next request will fetch the latest image from origin.

CDN invalidation is useful, but it can be slow or expensive depending on the CDN provider.

So, for static assets, we often use cache busting.

# CACHE BUSTING

Cache busting means changing the file name or URL when the content changes. For example -

    app.js

If we cache this for 30 days and later change the JS file, some users may still see the old version. So, instead of using the same name, we use versioned names.

For example -

    app.v1.js
    app.v2.js

OR

    app.8f3a9.js

Now, when the file changes, the URL changes and the CDN and browser treat it as a new file. So, we do not need to delete the old cache immediately.

This is very common for frontend assets like JS, CSS, and images.

# BENEFITS AND DOWNSIDES OF CDNs

Some benefits of CDN are -

    1. Lower latency
    2. Faster page load
    3. Lower origin server load
    4. Better global performance
    5. Better scalability
    6. Helps handle traffic spikes
    7. Can improve availability
    8. Reduces bandwidth cost in many cases
    9. Can provide DDoS protection
    10. Can serve large files efficiently

For example, if a video is watched by users around the world, serving it using a CDN is much better than serving it using one origin server.

CDN also has some downsides. The first downside is the stale content. If the content changes at origin but the CDN still has the old content, users may see stale data.

The second downside is cache invalidation complexity.

We need to decide how long the content should be cached and how to refresh it.

The third downside is debugging difficulty.

Sometimes, the origin server has the correct data but the CDN is serving the old data. This can confuse the developers.

The fourth downside is risk with private data. If the cache rules are not correct, the private user data may accidentally be cached by the CDN. This is a serious problem.

So, CDNs should be configured carefully.

# CDN AND SECURITY

CDNs can improve security in some ways. For example, many CDNs provide DDoS protection, Web Application Firewall, TLS termination, Bot protection, and Rate Limiting.

Since traffic passes through CDN before reaching origin, CDN can block some bad traffic early.

But CDN is not a replacement for application security.

The application still needs authentication, authorization, validation, and proper access control.

Also, CDN cache rules must be configured carefully to avoid caching private data.

# CDN VS REVERSE PROXY CACHE

CDN and reverse proxy cache are related. Both can cache responses before they reach the application.

But they are usually placed differently.

CDN is geographically distributed and closer to users. Reverse proxy cache is usually closer to the application servers.

    User -> CDN -> Reverse Proxy -> App Server -> Database

CDN helps with global delivery. Reverse proxy cache helps reduce load on app servers inside your infrastructure.

# WHEN TO USE CDNs?

Use CDN when -

    1. Users are geographically distributed
    2. Static files are requested frequently
    3. Website needs faster page load
    4. Origin server load should be reduced
    5. Large files need to be delivered
    6. Traffic spikes are expected
    7. Public content can be cached safely

Some good examples are -

    1. E-commerce product images
    2. Video streaming
    3. News websites
    4. SaaS frontend assets
    5. Mobile app downloads
    6. Public documentation sites
    7. Blog and media content

CDN is especially useful when users are spread across many regions.

Be careful with CDNs when -

    1. Content is user-specific
    2. Data changes very frequently
    3. Strong real-time freshness is required
    4. Responses contain private information
    5. Cache headers are not well understood
    6. Invalidation must happen immediately

For example, do not publicly cache -

    1. Bank balance page
    2. User order history
    3. Private dashboard
    4. Payment page
    5. Admin panel response

These should either not be cached by CDN or should use private/no-store rules.
