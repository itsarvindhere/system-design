Local and Distributed Caching means understanding where the cache is stored and how many application servers can use it.

As we know, caching means storing the frequently used data in a faster place so future requests can be served quickly.

But, there is one important question -

    Where to store the cache?

It can be stored inside the application server itself or it can be stored in a separate shared cache system like Redis.

Based on this, caching can be divided into two common types -

    1. Local Cache
    2. Distributed Cache

# LOCAL CACHE

It means the cache is stored inside the same application instance. For example, if we have one backend server then the app server can keep some frequently used data in its own memory.

Since this cache is inside the same server, it is very fast.

The application does not need to make a network call to Redis or another cache system as it can directly read from its own memory.

So, the flow becomes -

    1. Request comes in
    2. App checks local memory cache
    3. If found, return data
    4. If not found, fetch from database
    5. Store in local cache
    6. Return data

This is simple and fast.

Local cache is good for things like -

    1. Configuration values
    2. Feature flags
    3. Static reference data
    4. Small lookup tables
    5. User permissions for a short time
    6. Computed values used repeatedly by the same server

The main problem with the Local Cache is that it is not shared. This means, if we have multiple application servers, then each server will have its own local cache. So, the same key may have different values on the different servers.

For example -

    App Server 1 cache:
        product:123 price = Rs. 1000

    App Server 2 cache:
        product:123 price = Rs. 900

    App Server 3 cache:
        product:123 not cached

This can happen because each server manages its own memory. If product price changes, invalidating the local cache on all servers becomes harder.

This is called cache inconsistency.

So, the local cache works the best when the cached data is either not very sensitive to freshness or when each server can safely keep its own copy.

# DISTRIBUTED CACHE

Distributed Cache means that the cache is stored in a separate shared cache system. Multiple application servers can use the same cache. For example -

    App Server 1 \
    App Server 2  -> Redis -> Database
    App Server 3 /

So, here Redis is shared by all the application servers.

If App Server 1 stores product:123 in Redis, App Server 2 can also read it.

This makes distributed cache useful in large systems with many application servers.

Distributed cache is useful because modern applications usually run on multiple servers. For example, during heavy traffic, we may scale the backend horizontally - 

    App Server 1
    App Server 2
    App Server 3
    App Server 4
    App Server 5

If every server only has its own local cache, the same data may be loaded again and again on each server.

But with distributed cache, all servers can reuse the same cached data. This reduces duplicate work.

So, the benefits are -

    1. Shared across multiple app servers
    2. Better cache hit ratio
    3. Easier invalidation than many local caches
    4. Can store larger data than local memory
    5. Useful for sessions, rate limits, and shared data
    6. Works well in horizontally scaled systems

Some common tools for distributed cache are Redis, Memcached, Hazelcast, and Aerospike. Redis is one of the most common choices.

Distributed Cache is commonly used for -

    1. User sessions
    2. Product details
    3. API responses
    4. Rate limiting counters
    5. User profile data
    6. Authentication tokens
    7. Leaderboards
    8. Frequently accessed database results

For example, session data should often be shared. If a user logs in and their session is stored only in App Server 1 local memory, then what happens if the next request goes to App Server 2?

App Server 2 may not know about the session.

So, session data is commonly stored in a distributed cache like Redis.

## PROBLEMS WITH DISTRIBUTED CACHING

Distributed cache is powerful, but it also has downsides.

The first downside is network latency.

Since Redis or Memcached is a separate system, the application must make a network call. So, distributed cache is slower than local memory cache.

The second downside is operational complexity.

Now we need to manage another system. For example -

    1. Redis deployment
    2. Redis memory limits
    3. Replication
    4. Failover
    5. Monitoring
    6. Cache eviction policy
    7. Network issues

The third downside is that distributed cache can become a dependency. If Redis goes down, many application requests may become slower or fail.

So, distributed cache should be designed carefully.

# MULTI-LEVEL CACHING

Sometimes systems use both local and distributed caching. This is called multi-level caching. For example -

    Local Cache -> Redis -> Database

The flow can be -

    1. App checks local cache
    2. If found, return data
    3. If not found, check Redis
    4. If found, store in local cache and return data
    5. If not found, fetch from database
    6. Store in Redis
    7. Store in local cache
    8. Return data

This gives the speed of local cache and the sharing of distributed cache.

But, multi-level caching also increases complexity.

Now the same data exists in multiple places.If data changes, we may need to invalidate both local cache and Redis.

So, multi-level caching should be used only when the performance benefit is worth the complexity.

# WHEN TO USE WHAT?

Use local cache when -

    1. Data is small
    2. Data is read very frequently
    3. Slight staleness is acceptable
    4. Each app server can keep its own copy
    5. Very low latency is required
    6. Data does not change very often

Some good examples are -

    1. Feature flags
    2. App configuration
    3. Static reference data
    4. Country codes
    5. Currency metadata
    6. Permission rules for a short time

Local cache is best when speed matters and sharing is not very important.

Use distributed cache when -

    1. Multiple app servers need shared cached data
    2. Cache invalidation should happen in one place
    3. Data is expensive to fetch from database
    4. Cache hit ratio should improve across servers
    5. Data is needed by many instances
    6. We need shared counters or shared sessions

Some common examples are -

    1. User sessions
    2. Product details
    3. User profiles
    4. API responses
    5. Rate limiting counters
    6. Leaderboards
    7. Authentication tokens

So, Distributed cache is best when sharing matters.

A good approach is -

    Local cache for very hot small data
    Distributed cache for shared application data
    Database as the source of truth
