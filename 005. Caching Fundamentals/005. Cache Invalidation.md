What if the database changes but the cache still has the old value?

In that case, the cache becomes stale.

For example, let's say we are caching product details in an e-commerce app. So, if we have a situation where -

    Database:
        product:123 price = Rs. 900

    Cache:
        product:123 price = Rs. 1000

Now, if the application returns data from the cache, the users will see the wrong price. This is a problem.

Cache Invalidation means removing or updating cached data when the original data changes. It is the process of making sure that the old or incorrect cached data is removed or refreshed.

# WHY DO WE NEED CACHE INVALIDATION?

Caching improves performance but the data can change. For example -

    1. Product price may change
    2. Inventory count may change
    3. User profile may be updated
    4. Order status may change
    5. User permissions may change
    6. Configuration values may change

If the cache is not invalidated, users may continue seeing the old data.

For example, If the user changes their profile picture but the cache still stores the old one, the application may keep showing the old picture.

Or,

If the inventory count changes, but cache still has the old count, the system may show wrong stock information.

So, Cache Invalidation is needed to keep the cached data reasonably fresh.

The main goal is to balance Performance and Freshness.

If we invalidate the cache too often, the cache becomes less useful because many requests will go to the database.

If we invalidate the cache too late, users may see old data.

So, it is about deciding when cached data should no longer be trusted.

# CACHE INVALIDATION STRATEGIES

## 1. TTL-BASED STRATEGY

TTL means Time To Live. In TTL-based invalidation, the cache entry is stored only for a fixed amount of time. For example -

    Product details -> cache for 10 minutes
    User profile -> cache for 5 minutes
    Homepage feed -> cache for 30 seconds
    OTP -> cache for 5 minutes

So, once the TTL expires, the cache entry is removed or treated as invalid. The benefit here is that this is very simple to implement. We do not need any complex logic to detect every data change. Even if the data becomes stale, it will only remain stale until the TTL expires.

But, it has a downside.

Suppose, the product price changes just after the product was cached for 10 minutes. This means, the users may see the old price for almost 10 minutes. So, TTL reduces stale data, but it does not completely remove the stale data.

TTL is useful when some amount of staleness is acceptable.

For example -

    1. Homepage data
    2. Trending posts
    3. Product listing pages
    4. Public API responses
    5. Analytics dashboards

TTL is simple and common, but the TTL duration should be chosen carefully. If TTL is too long, then stale data may live too long. If TTL is too short, the cache hit ratio may become slow.

## 2. DELETE CACHE ON WRITE

In this strategy, whenever data changes in the database, we delete the related cache entry. 

The flow is -

    1. Update database
    2. Delete cache key
    3. Next read gets cache miss
    4. Fetch latest data from database
    5. Store latest data in cache again

Let's say for a product, the price is updated -

    Database updated:
        product:123 price = Rs. 900

Now, we delete -

    Cache delete:
        product:123

So, the next time someone requests product 123, the cache will not have it. The application will fetch the latest value from the database and store it in the cache again. This is very common with Cache-Aside pattern.

The benefit is that this is simpler than updating the cache manually. We do not need to calculate and store the new cached value immediately. We just remove the old value.

The downside is that the next read after invalidation is slower because it has to go to the database. But, in many systems, this is acceptable.

This is one of the most practical cache invalidation strategies.

## 3. UPDATE CACHE ON WRITE

In this, whenever data changes in the database, the cache is updated with the latest value. So, the flow is -

    1. Update database
    2. Update cache with new value
    3. Future reads get latest data from cache

For example, if the product price changes to 900 -

    Database:
        product:123 price = Rs. 900

    Cache:
        product:123 price = Rs. 900

The benefit is that the cache stays warm so the future reads can still be served from the cache. But, this strategy is more complex because what if the database update succeeds but the cache update fails? Then, the database will have the new value but the cache still has the old one.

Also, sometimes, the cached data is not exactly the same as the database row. It may be a computed response or a combined result from multiple tables. So, in that case, updating the cache correctly can become difficult.

So, update cache on write is useful when the cache value is simple and easy to update. For complex cached data, deleting the cache is often easier.

## 4. EVENT-BASED INVALIDATION

In large distributed systems, many services may cache the same data. For example, the product data may be used by Product Service, Search Service, Recommendation Service, Cart Service, and the CDN or API Gateway.

If the product changes, all these cached copies may need to be invalidated.

In such cases, even-based invalidation can be used.

The flow is -

    1. Product Service updates product in database
    2. Product Service publishes ProductUpdated event
    3. Other services consume the event
    4. Other services delete or update their cached data

This is useful in microservices because the service that changes the data does not need to directly call every other service. It just publishes one event.

But, the event-based invalidation also has challenges. Events can be delayed. Consumers can fail. Some services may miss the event.

So, this is often combined with TTL.

That way, even if an invalidation event is missed, the stale data will eventually expire.

## 4. MANUAL INVALIDATION

Sometimes, cache is invalidated manually. For example -

    1. Admin clears homepage cache
    2. Developer purges CDN cache after deployment
    3. Operations team clears config cache
    4. Support team refreshes user-specific cached data

Manual invalidation is useful for rare cases. For example, if a wrong image was cached by the CDN, we may manually purge that CDN cache. But, manual invalidation should not be the main strategy for regular data changes. If the data changes frequently, invalidation should be automatic.

# CACHE INVALIDATION ACROSS LAYERS

Cache Invalidation becomes harder when the same data is cached in multiple layers.

For example, product data or page data may be cached in Browser Cache, CDN cache, Reverse proxy cache, Application cache, and Local in-memory cache.

Let's say the product price changes.

If we only delete the Redis cache, the CDN may still serve an old page.

If only purge the CDN, the application cache may still have the old data.

So, layered caching needs a clear invalidation strategy. Different layers may need different TTL. For example -

    Browser cache:
        Longer TTL for static assets

    CDN cache:
        Medium TTL for public content

    Application cache:
        Shorter TTL for dynamic data

For static assets like JavaScript, CSS, and images, we often use versioned file names. For example -

    app.v1.js
    app.v2.js

Instead of trying to delete old browser cache, we change the file name so the browser sees it as a new file and downloads it again. This is called 'Cache Busting.

# RACE CONDITION IN CACHE INVALIDATION

A race condition can happen when the read and write operations happen at the same time. For example -

    1. Request A reads old product data from database
    2. Request B updates product data in database
    3. Request B deletes product cache
    4. Request A stores old product data back into cache

Now, even though we deleted the cache, old data got written back into the cache again. This is a race condition.

These problems are more common in high traffic systems.

Some ways to reduce these problems are -

    1. Use short TTL
    2. Delete cache after database update
    3. Use version numbers in cache values
    4. Use locks for hot keys when needed
    5. Avoid caching highly sensitive rapidly changing data

We may not need all these in every system. The solution depends on how important freshness is.

# CACHE INVALIDATION VS CACHE EVICTION VS CACHE EXPIRATION

They sound the same but they are not.

Cache invalidation happens because the cached data is no longer correct.

Cache Eviction happens because the cache needs space.

Cache Expiration usually happens because the TTL is over.

Invalidation is about correctness while Eviction is about capacity.

Expiration is time-based while Invalidation is change-based.

In real-systems, all these are used together.
