Cache Avalanche is a problem that happens when many cache entires expire or become unavailable at the same time. As we know, the cache protects the database by serving frequently requested data quickly.

Normally, the flow is -

    Request -> Cache hit -> Return data

Ths keeps the traffic away from the database.

But, suppose many cached keys expire at the same time. Now, many requests will get cache misses together. So, instead of being served from the cache, a large amount of traffic suddenly goes to the database.

This sudden heavy load can overload the database.

This problem is called Cache Avalanche.

# WHY DOES CACHE AVALANCHE HAPPEN?

Cache Avalanche mainly happens for two reasons -

    1. Many cache keys expire at the same time
    2. The cache system goes down

## 1. MANY CACHE KEYS EXPIRE TOGETHER

Suppose, we cache many product details at the same time -

    product:1 -> TTL 10 minutes
    product:2 -> TTL 10 minutes
    product:3 -> TTL 10 minutes
    product:4 -> TTL 10 minutes
    product:5 -> TTL 10 minutes

If all these keys were added at the same time, they may also expire at the same time.

So, after 10 minutes, many requests will miss the cache together and the database suddenly receives traffic for many different keys.

This can create a large spike in the database load.

## 2. CACHE SYSTEM GOES DOWN

Another case is when the cache itself becomes unavailable.

For example, Redis goes down.

Now, the application cannot read from the cache at all. So, the traffic that was earlier served by Redis may directly go to the database.

This sudden shift can overload the database.

So, cache avalanche can happen either because many keys expire together or because the cache layer fails.

# CACHE AVALANCHE VS CACHE STAMPEDE

Cache avalanche and cache stampede are related, but they are not exactly the same.

Cache stampede usually happens when one very popular cache key expires.

For example -

    homepage:data expires
    Thousands of requests ask for the same key
    All try to rebuild the same cache entry

So, stampede is usually about one hot key.

Cache avalanche happens when many cache keys expire together or the cache layer becomes unavailable.

For example -

    product:1 expires
    product:2 expires
    product:3 expires
    product:4 expires
    Redis goes down

So, avalanche is usually about many keys or the whole cache layer.

Both can overload the database. But the scale is different.

# HOW TO PREVENT CACHE AVALANCHE

## 1. RANDOMIZED TTL

Randomized TTL means adding some randomness to cache expiry times. Instead of giving every key the exact same TTL, we add a small random variation.

For example, instead of -

    TTL = 60 minutes for every product

We can use -

    product:1 -> TTL 58 minutes
    product:2 -> TTL 63 minutes
    product:3 -> TTL 55 minutes
    product:4 -> TTL 61 minutes

Now, all keys will not expire at the same time.

Their expiry will be spread over time.

This reduces sudden load spikes.

This is one of the simplest and most useful ways to prevent cache avalanche.

## 2. CACHE WARMING

Cache warming means loading important data into cache before traffic needs it.

For example, after deployment or Redis restart, cache may be empty. If users immediately start sending requests, many requests may hit the database.

So, we can warm the cache by preloading important keys. For example -

    1. Homepage data
    2. Popular products
    3. Trending categories
    4. Common configuration
    5. Frequently accessed user permissions

This helps reduce sudden cache misses.

Cache warming is useful when we already know which data is likely to be requested. But it should be used carefully. If we warm too much data, we may waste memory and backend resources.

## 3. REFRESH AHEAD

Refresh-ahead means refreshing cache before it expires. For example, suppose a cache key has TTL of 10 minutes.

If it is still being used frequently, the system can refresh it after 9 minutes in the background. So, the flow is -

    1. Cache entry is close to expiry
    2. Background job refreshes it
    3. Users continue getting cache hits

This is useful for popular data. It reduces the chance that many users will hit expired keys at the same time.

## 4. MULTI-LEVEL CACHE

A multi-level cache means using more than one cache layer. For example -

    Local memory cache -> Redis -> Database

If Redis has a problem, the local cache may still serve some hot data for a short time.

OR -

    CDN -> Reverse Proxy -> Application Cache -> Database

If one layer misses, another layer may still protect the database.

Multi-level cache does not completely remove avalanche risk, but it reduces the chance that all traffic directly reaches the database at once.

The downside is that invalidation becomes harder because the same data may exist in multiple places.

## 5. CACHE HIGH AVAILABILITY

If the cache itself goes down, it can cause avalanche. So, the cache system should be highly available. For Redis, this may mean -

    1. Redis replication
    2. Redis Sentinel
    3. Redis Cluster
    4. Failover setup
    5. Monitoring
    6. Backups where needed

The goal is -

    Cache failure should not immediately bring down the database.

A cache is a performance layer, but in high traffic systems, the database may depend on it for protection.

So, cache availability matters.

## 6. FALLBACK AND CIRCUIT BREAKER

If cache fails, the application should not blindly send all traffic to the database. We can use fallback behavior. For example -

    1. Return stale local data if available
    2. Return a degraded response
    3. Temporarily disable expensive features
    4. Rate limit some requests
    5. Use circuit breaker to protect database

A circuit breaker stops sending too many requests to an unhealthy dependency.

For example, if the database is overloaded, the application may stop some non-critical calls temporarily. This protects the system from complete failure.

For example, if recommendations are unavailable, we can show an empty recommendation section. That is better than taking down the whole product page.

# BEST PRACTICES

Some good practices to prevent cache avalanche are -

    1. Add random jitter to TTL
    2. Avoid setting the same expiry time for many keys
    3. Warm important cache keys after restart or deployment
    4. Use refresh-ahead for hot data
    5. Make cache highly available
    6. Use multi-level caching where useful
    7. Use fallback responses during cache failure
    8. Protect database with rate limiting or circuit breaker
    9. Monitor cache hit ratio
    10. Monitor sudden cache miss spikes
    11. Monitor database load after cache expiry


A practical approach is -

    Random TTL + Cache Warming + Refresh Ahead + Fallback

This means -

    1. Do not let keys expire together
    2. Preload important data when needed
    3. Refresh hot data before expiry
    4. Protect database when cache is unhealthy
