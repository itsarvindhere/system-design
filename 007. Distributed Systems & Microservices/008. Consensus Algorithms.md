Consensus Algorithms are the algorithms used in distributed systems to help multiple nodes agree on one value, one decision, or one shared state even when failures happen.

In a single machine system, making a decision is simple because one process can decide locally.

But, in a distributed system, many nodes may each have different information, different timing, or temporary communication problems.

So, the question becomes -

    How do multiple independent machines agree on one result?

This is what consensus is all about.

We need consensus when distributed nodes must agree on something important. For example -

    Who is the leader?
    Which value should be committed?
    Did this operation succeed?
    Which node owns a resource?
    What is the next configuration of the cluster?

If different nodes believe different answers, the system can become inconsistent or unsafe.

For example -

    Two nodes both think they are the leader
    Two replicas commit different values
    Two coordinators both grant the same lock

These are dangerous situations.

So, consensus algorithms are used to avoid such disagreement.

Consensus is not only about voting once. It is about reaching agreement safely in the presence of failures, delays, and uncertainty.

Consensus is hard because distributed systems are hard. Some common difficulties include -

    1. Nodes may crash
    2. Messages may be delayed
    3. Messages may be lost
    4. Network partitions may happen
    5. Clocks are not perfectly synchronized
    6. Nodes may see events in different orders

For example -

    Node A thinks leader is alive
    Node B thinks leader is dead
    Node C cannot hear A because of network issue

Now how should the system agree on what is true? This is why consensus is one of the deepest problems in distributed systems.

# SAFETY AND LIVENESS

Consensus algorithms are usually designed around two big goals -

    1. Safety
    2. Liveness

Safety means the system should not reach an incorrect decision. For example -

    Two different leaders should not both be accepted as valid
    Two conflicting values should not both be committed

Liveness means the system should keep making progress when conditions are good enough. For example -

    If enough nodes are healthy and can communicate
    The system should eventually choose a leader
    Or commit a value

So -

    Safety = do not do the wrong thing
    Liveness = eventually do the needed thing

# MAJORITY QUORUM

Many consensus algorithms use the idea of a majority quorum. A quorum means a minimum number of nodes required to make a valid decision.

A common quorum is a majority.

For example -

    3 nodes -> majority is 2
    5 nodes -> majority is 3
    7 nodes -> majority is 4

The reason majority matters is that two majorities must overlap. That overlap helps prevent conflicting decisions.

For example, if one leader election needed approval from 3 out of 5 nodes, and another conflicting election also needed 3 out of 5, at least one node would be common between the two groups.

That shared node helps preserve consistency.

This is one of the key ideas behind many consensus systems.

# LEADER-BASED QUORUM

Many practical consensus algorithms are leader-based.

That means, one node is chosen as the leader, and the leader coordinated some decisions.

For example -

    Leader receives a write
    Leader proposes it to followers
    Followers acknowledge
    Once enough agree, the value is committed

Leader-based design simplifies coordination because not every node tries to decide independently at the same time.

But it also means leader election becomes important.

If the leader fails, the system must choose a new one safely.

# COMMON USE CASES

Consensus algorithms are used in many important distributed system tasks like -

    1. Leader election
    2. Replicated log agreement
    3. Metadata management
    4. Configuration changes
    5. Cluster membership
    6. Distributed locks in some systems
    7. Coordination services
    8. Database replication control

Systems like distributed databases, coordination services, and cluster managers often depend on consensus.

# PAXOS

Paxos is one of the most famous consensus algorithms. It is very important historically and theoretically.

The core goal of Paxos is to let distributed nodes agree on a value even when some nodes fail.

Paxos is known for being correct and powerful, but also difficult to understand and implement.

That is why many engineers know Paxos is important, but often learn Raft first because it is easier to reason about.

You do not need every detail at the beginning. The important point is -

    Paxos is a foundational consensus algorithm
    It focuses on safe agreement despite failures

# RAFT

Raft is another algorithm that is designed to be easier to understand than Paxos. Raft is very popular in practice and in teaching.

Raft usually explains consensus through a replicated log and a clear leader model. The main ideas are -

    Leader election
    Log replication
    Safety rules
    Term numbers
    Majority acknowledgement

A simple mental model is -

    One leader accepts writes
    Leader sends log entries to followers
    Once majority acknowledges, the entry is committed
    If leader fails, a new leader is elected

Raft is widely used because it is more approachable while still providing strong guarantees.

# NETWORK PARTITIONS AND CONSENSUS

Consensus becomes especially tricky during network partitions.

A network partition means some nodes cannot communicate with others.

For example -

    5 node cluster
    2 nodes on one side
    3 nodes on another side

Now the system must avoid split brain.

Usually only the side with majority quorum should continue making decisions. The minority side should stop acting as if it has full authority.

This is why quorums matter so much.

Without that rule, both sides might continue independently and create conflicting state.

# FAILURE TOLERANCE

Consensus algorithms do not require all nodes to be alive all the time.

They are usually designed so the system can continue if enough nodes remain available.

For example, in a 5-node cluster -

    Up to 2 nodes may fail
    But 3 working nodes are still enough for majority

If too many nodes fail, the system may stop making progress. This is a liveness issue. But it should still try to preserve safety. That is a major design principle.

# TRADEOFFS

Consensus algorithms provide strong coordination, but they come with costs. Some tradeoffs are -

    More message exchange
    Higher write latency
    More operational complexity
    Need for odd-sized clusters
    Possible reduced availability during leader loss
    Harder implementation than simple replication

So, consensus is powerful, but not free. This is why not every distributed system uses a consensus algorithm for everything.

Consensus is needed when disagreement would be dangerous. For example -

    Choosing one leader
    Committing one source of truth
    Coordinating critical metadata
    Ensuring only one value becomes official
    Managing distributed configuration safely

If the system can tolerate looser consistency, simpler approaches may sometimes be enough. So, consensus should be used where the guarantee is truly worth the cost.

Remember that Consensus is about safe agreement under uncertainty. The problem is not hard because nodes are far apart. The problem is hard because nodes can fail, messages can be delayed, and different parts of the system can temporarily believe different things.
