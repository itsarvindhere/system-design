Circuit Breaker is a resilience pattern that is used in distributed systems to stop repeated calls to failing service for some time.

In a distributed system, one service often depends on another service. For example -

    Order Service calls the Payment Service
    API Service calls the User Service
    Checkout Service calls the Inventory Service

So, if the downstream service becomes slow or starts failing, the caller may keep sending more requests to it.

That creates problems like -

    More waiting
    More timeouts
    More resource usage
    More thread or connection exhaustion
    More pressure on an already unhealthy service

So, instead of continuing to send requests blindly, the system can temporary stop calling that failing service.

This is the main idea of a Circuit Breaker.

The idea comes from the electrical systems.

In electricity, a circuit breaker opens the circuit when something goes wrong, so the damage does not continue.

In software, a circuit breaker opens when failures cross a threshold, so the system stops sending more requests to the unhealthy dependency.

This protects both the caller and the failing service.


# WHY TO USE A CIRCUIT BREAKER?

Without a circuit breaker, failure can spread. For example -

    Payment Service becomes slow
    Order Service keeps waiting on it
    Order Service threads become busy
    Queue of waiting requests grows
    Order Service itself becomes slow or fails

Now, one failing dependency starts affecting other services. This is how cascading failures happen. Circuit breaker helps stop that spread.

Instead of waiting again and again for a known failing dependency, the caller fails fast.

This gives the system a chance to protect resources and recover more gracefully.

# THE MAIN IDEA

A circuit breaker watches requests to a dependency. It tracks things like -

    1. Failures
    2. Timeouts
    3. Error rate
    4. Slow responses

If failures are too frequent, the circuit breaker changes state and stops normal calls to that dependency for some time.

A simple flow may look like this -

    Request goes to downstream service
    Downstream service fails repeatedly
    Failure threshold is reached
    Circuit breaker opens
    New requests fail fast without calling downstream
    After some wait, system tests again
    If dependency recovers, normal flow resumes

This is the standard behavior.

# THREE COMMON STATES

A circuit breaker usually has three states.

    1. Closed
    2. Open
    3. Half-Open

## 1. CLOSED STATE

Closed means normal operation. Requests are allowed to go through.

The circuit breaker still monitors the results, but it does not block the traffic. So -

    Closed = dependency is assumed usable

## 2. OPEN STATE

Open means the circuit breaker has detected too many failures. Now, the requests are not send to the downstream service. Instead, they fail immediately or use fallback behavior.

So -

    Open = stop sending requests for now

## 3. HALF-OPEN STATE

Half-open is a testing state.

After some cool down period, the circuit breaker allows a small number of requests to go through.

If those requests succeed, the circuit can close again. If they fail, the circuit opens again.

So -

    Half-Open = cautiously test recovery

This prevents the system from fully trusting the dependency too soon.

# FAIL-FAST

One of the biggest benefits of a circuit breaker is fail-fast behavior.

Fail fast means the system quickly stops trying an operation that is likely to fail.

For example, instead of doing this -

    Wait 10 seconds
    Timeout
    Retry
    Wait again
    Timeout again

The service may immediately return -

    Payment temporarily unavailable

This is often much better than making every request wait for a hopeless downstream call.

Fail-fast behavior improves the system stability and often improves user experience.

# HOW CIRCUIT BREAKER DECIDES TO OPEN?

Different systems use different rules. Some common triggers include -

    1. Consecutive failure count
    2. Failure percentage
    3. Timeout rate
    4. Slow call rate

For example - 

    If more than 50% of the last 20 requests fail,
    Open the Circuit

OR

    If 5 requests in a row time out
    Open the Circuit

The exact threshold depends on the system and business need.

# COOLDOWN PERIOD

When a circuit opens, it usually stays open for a fixed amount of time. This is called a Cooldown Period or Sleep Window.

For example -

    Circuit opens for 30 seconds
    No calls are sent during that time
    After 30 seconds, a small test is allowed

This gives the downstream service time to recover. Without a cooldown period, the caller may keep testing too aggressively.

# FALLBACK

Sometimes, a circuit breaker works together with a fallback behavior.

Fallback means the system does something simpler when the real dependency is unavailable.

For example -

    Return cached data
    Show default response
    Skip non-critical feature
    Return 'temporarily unavailable'
    Queue work for later

For example, if Recommendation Service is down, the system may show popular products instead of personalized recommendations.

Fallback helps graceful degradation.

# BENEFITS AND CHALLENGES

Circuit Breaker gives several benefits like -

    1. It prevents cascading failures
    2. It reduces wasted waiting
    3. It protects threads, connections, and resources
    4. It helps failing services to recover
    5. It enables graceful degradation
    6. It improves resilience

These benefits are why circuit breaker is a very common resilience pattern in microservices.

But, a circuit breaker pattern also creates some tradeoffs -

    1. Threshold tuning is tricky
    2. It may open too aggressively
    3. It may stay closed too long
    4. Recovery detection is imperfect
    5. Bad fallback logic can confuse users
    6. It adds operational complexity

For example, if thresholds are too sensitive, the circuit may open even during short temporary blips. If thresholds are too loose, the system may suffer before protection starts.

So tuning matters.

Some common mistakes are -

    1. Using retries without circuit breaker
    2. Having no timeout with circuit breaker
    3. Setting bad thresholds
    4. Opening the circuit for too long or too little time
    5. No fallback or poor fallback
    6. Not monitoring circuit state changes

A circuit breaker should be observable. Teams should know -

    How often it opens
    Which dependency is unstable
    Whether fallback is being used
    How long recovery takes

One important thing to remember is that Circuit breaker does not fix the dependency. It protects the caller from repeatedly suffering because of that dependency.
