Heartbeats are periodic signals send by a service, node, or process to show that it is still alive.

In distributed systems, one machine often needs to know whether another machine is healthy and still running.

But, machines do not constantly know that automatically.

So, the system uses heartbeats. The idea is simple -

    A node sends small "I am alive" signals repeatedly
    Other nodes or a monitoring system expect those signals
    If heartbeats stop arriving, the node may be considered failed

But, why do we need heartbeats?

Well, in distributed systems, machines can fail in many ways. For example -

    1. Process crashes
    2. Server goes down
    3. Network path breaks
    4. Node becomes unresponsive
    5. Service gets stuck
    6. Container is killed

Other parts of the system need some way to notice this. If they keep assuming the node is healthy, they may send the traffic to a dead instance and then wait forever for the response.

So, heartbeats help the system detect that something may have gone wrong.

Heartbeats are one of the most common mechanisms for failure detection.

A Heartbeat is usually a lightweight periodic message. For example, Every 5 second, a service sends -

    "I am alive"

OR

    A worker updates its lease timestamp regularly

OR

    A database replica sends regular health signals to a coordinator

The message is usually small because its purpose is not to send business data. Its purpose is to prove liveness.

Heartbeats can happen in different ways depending on the system.

For example -

    Service instance -> Service registry
    Follower node -> Leader
    Leader -> Followers
    Worker -> Job coordinator
    Node -> Cluster manager
    Application -> Monitoring system

So, they are not tied to one specific architecture.

They are a general distributed system idea.

For example, lets say a service registry tracks healthy instances.

    Inventory Service instance starts
    It registers itself
    Every few seconds it sends heartbeat to registry
    Registry keeps marking it healthy

Now, imagine the instance crashes. Then -

    Heartbeats stop
    Registry notices missing heartbeats
    Registry marks instance unhealthy
    Traffic is no longer sent to it

This is a very common use of heartbeats.

# IMPORTANT LIMITATION

A missing heartbeat does not always mean the node is definitely dead. It may also mean -

    1. Network is delayed
    2. Network partition happened
    3. Node is overloaded
    4. Coordinator is slow
    5. Heartbeat message was dropped

This is very important. In distributed systems, failure detection is often based on suspicion, not absolute certainty.

So, heartbeats help detect likely failures, but they do not guarantee perfect truth. This is one reason distributed systems are hard.

# HEARTBEAT TIMEOUT

A heartbeat timeout is the duration the system waits before deciding that missing heartbeats indicate a problem. For example -

    Heartbeat every 5 seconds
    Timeout after 15 seconds

If no heartbeat is received within 15 seconds, the node may be considered failed.

Choosing the timeout is a tradeoff.

If the timeout is too short, the healthy nodes may be marked dead by mistake.

If the timeout is too long, failure detection becomes slow.

So, heartbeat setting needs balance. This is one of the most practical design decisions.

# PUSH VS PULL STYLE

Heartbeats can be designed in different ways.

In Push style, the node actively sends heartbeat messages. For example -

    Worker sends heartbeat to the coordinator every 10 seconds

This is very common.

In Pull style, another system checks the node periodically. For example -

    Load balancer sends health check request every few seconds

This is slightly different from the classic heartbeat, but the idea is similar.

In practice, distributed systems often use both heartbeats and active health checks together.

# HEARTBEATS VS HEALTH CHECKS

These two ideas are related but not exactly the same. Heartbeat usually means -

    "I am alive"

Health check usually means -

    "I am alive and possibly also ready or functioning correctly"

For example, a service may still send heartbeats but be unhealthy in a deeper sense because -

    1. Database connection is broken
    2. Internal queue is stuck
    3. Dependency is failing
    4. It cannot actually serve requests correctly

So, heartbeat is often a liveness signal. Health check is often a richer health signal.

This distinction matters.

# COMMON USE CASES

Heartbeats are used in many places like -

    1. Service registries
    2. Cluster memberships
    3. Leader election
    4. Distributed locks or leases
    5. Worker coordination
    6. Failover systems
    7. Replica monitoring
    8. Monitoring agents

Any place where one component needs to know whether another is still active may use heartbeats.

Suppose one node is the leader in a cluster. Other nodes may expect regular signals from that leader. For example -

    Leader sends heartbeat
    Followers keep accepting that leader
    Heartbeats stop
    Followers suspect leader failure
    New election may begin

This is one of the most important uses of heartbeats. They help systems notice when leadership may be lost.

Another example is Job processing.

Suppose a worker is processing a long-running job. The system may want to know whether the worker is still alive. For example -

    1. Worker picks job
    2. Worker sends heartbeat while processing
    3. Heartbeats stop unexpectedly
    4. Coordinator assumes worker failed
    5. Job may be reassigned

This helps avoid jobs being stuck forever. So, heartbeats are useful even beyond service discovery.

# CHALLENGES

Heartbeats are simple in idea but real systems still face challenges like -

    1. Network delays
    2. False failure suspicion
    3. Timeout tuning
    4. Partition handling
    5. Overloaded coordinators
    6. Split brain risk in some systems

For example, if two sides of a partition cannot hear each other, they both may believe the other side failed.

This can lead to dangerous situations depending on the system.

So, heartbeats are necessary, but they are not sufficient for solving all coordination problems.

Some common mistakes are -

    1. Treating missing heartbeat as perfect proof of death
    2. Setting heartbeat timeout too aggressively
    3. Ignoring network partitions
    4. Assuming heartbeat means full application health
    5. Not combining heartbeats with better health checks where needed
    6. Using one coordinator that becomes overloaded or a single point of failure

Remember that Heartbeats are mainly about liveness detection.

They help answer the question -

    "Is this node probably still alive?"4

But, they do not always answer -

    "Is this node fully healthy and safe to handle work?"
