# MICROSERVICES

Microservices is an architectural style where an application is built as a collection of small independent services.

Each service is responsible for a specific business capability and can be deployed and scaled separately.

So, instead of building one large application that does everything, we split the system into smaller services.

For example, an e-commerce system may have -

    1. User Service
    2. Order Service
    3. Payment Service
    4. Inventory Service
    5. Notification Service

Each service focuses on one area of responsibility.

This is the main idea of microservices.

## WHY TO USE MICROSERVICES?

We use microservices when a system becomes large enough that one single application becomes hard to manage.

As applications grow, problems may appear like -

    1. Codebase becomes too large
    2. Teams step on each other's changes
    3. Deployments become risky
    4. Scaling one part requires scaling everything
    5. One bug can affect the whole application
    6. Technology choices become harder to change

Microservices try to solve these problems by splitting the system into smaller independent units.

This can improve maintainability and scaling, but it also adds distributed systems complexity.

## CHARACTERISTICS OF MICROSERVICES

Microservices usually have these characteristics -

    1. Small focused services
    2. Each service owns a clear responsibility
    3. Services communicate over the network
    4. Services can be deployed independently
    5. Each service often owns its own data
    6. Failures are isolated more than in one large app

For example -

    Payment Service handles payment logic
    Inventory Service handles stock logic
    Notification Service handles email or SMS logic

The goal is not just making services smaller. The goal is to make boundaries clear.

## SERVICE BOUNDARY

A service boundary means what responsibility belongs inside one service and what responsibility belongs outside it.

For example -

    Order Service owns the order lifecycle
    Payment Service owns the payment lifecycle
    Inventory Service owns the stock lifecycle

A good microservice boundary is usually based on business capability, not random technical splitting. A bad splitting may look like this -

    One service for controllers
    One service for database access
    One service for validation

This is usually not a good microservices design. Good microservices are usually aligned with domain boundaries.

## DATA OWNERSHIP

In many microservices systems, each service owns its own database or data store. For example -

    User Service owns user data
    Order Service owns order data
    Payment Service owns payment data

Other services should usually not directly modify that data. Instead, they communicate through APIs or events.

This is important because it reduces tight coupling between services. But, it also makes distributed data consistency harder.

## MICROSERVICES ARE DISTRIBUTED SYSTEMS

This is very important. Once you use microservices, you are building a distributed system. That means, you can also inherit distributed systems problems like Network failures, Timeouts, Retries, Partial failure, Eventual Consistency, and Observability challenges.

So, microservices are not just a code organization style.

They are also an operational and architectural commitment.

# MONOLITH

A monolith is an application where all major business logic lives inside one deployable unit.

For example -

    One application codebase
    One deployment artifact
    Often one shared database

Different modules may exist inside it, but they run together as one application. For example, an e-commerce monolith may contain a User Module, an Order Module, a Payment Module, and an Inventory Module.

But, all of them are still part of one application.

Now, a monolith is not automatically bad. In fact, many systems start as monoliths and that is often a good choice.

## WHY MONOLITHS ARE USEFUL?

They are useful because they are simpler in many ways. For example -

    1. Easier local deployment
    2. Easier debugging
    3. Simpler deployment
    4. Simpler testing
    5. No network calls between internal modules
    6. Easier transactions inside one database
    7. Lower operational complexity

For small and medium systems, this simplicity is extremely valuable.

A lot of people underestimate this.

## WHY MOVE FROM MONOLITH TO MICROSERVICES?

Teams often move when the system or organization becomes large enough that the monolith starts slowing them down. There are some common reasons like -

    1. Codebase becomes too large
    2. Many teams work in the same repo
    3. Deployments become risky
    4. One hotspot needs separate scaling
    5. Team ownership is unclear
    6. One failure affects too much of the system

In such cases microservices can help. But, they are not free upgrade.

Many teams adopt microservices too early. This can create problems like -

    1. Too many services
    2. Hard local deployment
    3. Complex debugging
    4. Distributed data problems
    5. Too much operational overhead
    6. Slow delivery because of coordination cost

If the system is still small, a well-structured monolith is often the better choice.

A bad microservices system can be much worse than a good monolith.

# WHEN TO USE WHICH?

A monolith is a good choice when -

    1. Product is early
    2. Team is small
    3. Domain is still changing quickly
    4. Operational simplicity matters a lot
    5. One deployment unit is still manageable

For many startups and new products, monolith first is a very strong choice.

Microservices are often a good choice when -

    1. System has grown large
    2. Teams are large enough to own separate services
    3. Different parts need different scaling patterns
    4. Clear domain boundaries exist
    5. Team can handle operational complexity
    6. Independent deployment gives real value

Microservices should usually solve a real organizational or scaling problem. They should not be adopted only because they sound modern.

# MODULAR MONOLITH

There is also an important middle ground called a modular monolith.

This means -

    One deployable application
    BUT
    Strong internal module boundaries

For example -

    Order module
    Payment module
    Inventory module
    User module

Each module is cleanly separated inside the same application.

This often gives many benefits of good design without immediately taking on full distributed complexity.

That is why modular monolith is a very practical approach.

The real comparison is not -

    Monolith = bad
    Microservices = good

That is too simplistic.

A better understanding is -

    Monolith is simpler but less flexible at large scale
    Microservices are more flexible at large scale but much more complex

So, the question is now -

    "Which one is better in general?"

The real question is -

    "Which one fits the current size, team, and system needs?"
