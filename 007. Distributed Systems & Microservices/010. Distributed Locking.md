Distributed Locking is a way to make sure that across multiple machines or multiple services, only one participant can hold the right to perform a certain action at a time.

In a single process, locking is easier. For example -

    One thread acquires a mutex
    Other threads wait
    Only one thread enters the critical section

But, in distributed systems, the problem is harder because the competing workers are on different machines. So, the question now becomes -

    How do many independent services agree that only one of
    them should do this work right now?

That is what distributed locking is about.

We need distributed locking when multiple nodes may try to do the same sensitive work at the same time, but only one should be allowed.

For example -

    Only one worker should process a scheduled job
    Only one node should run a leader-only task
    Only one service instance should modify a shared resource
    Only one migration should run at a time
    Only one process should hold a lease on a resource

Without coordination, multiple nodes may all think they are allowed to proceed. This can cause problems like -

    Duplicate work
    Data corruption
    Double execution
    Race conditions
    Conflicting updates

So, distributed locking helps create mutual exclusion across machines.

# THE MAIN IDEA

The main idea is simple -

    Many nodes want access to one shared resource
    One node acquires the lock
    Other nodes do not proceed until the lock is released or expires

So, the lock represents temporary ownership. The node holding the lock is allowed to do the protected work. Other nodes must wait, retry later, or give up.

Suppose three workers are trying to process the same scheduled billing task. Without distributed locking -

    Worker 1 starts billing job
    Worker 2 also starts billing job
    Worker 3 also starts billing job

Now the same billing work may happen three times.

But, with distributed locking -

    Worker 1 acquires lock: billing-job-lock
    Worker 2 fails to acquire lock
    Worker 3 fails to acquire lock
    Only Worker 1 runs the billing job

This is the core purpose of distributed locking.

## LOCK OWNER

A distributed lock usually has an owner. The owner may be - 

    Worker ID
    Service instance ID
    Node ID
    Process ID
    Random token

This matters because the system should know who currently holds the lock.

It also matters during release. A service should not accidentally release a lock owned by someone else. That is an important safety detail.

## LOCK KEY

A lock is usually associated with a key or resource name. For example -

    order-123-lock
    billing-job-lock
    leader-election-lock
    inventory-sync-lock

This tells the system what resource is being protected. Different resources may have different keys.

## LEASE STYLE LOCKING

In distributed systems, locks are often implemented as leases instead of permanent locks.

A lease means the lock is valid only for some limited time unless it is renewed.

For example -

    Worker acquires lock for 30 seconds
    Worker renews it every 10 seconds
    If worker dies, lease eventually expires

In local systems, a crashed process may release a lock when process exits.

But, in distributed systems, a crashed machine may not clean up nicely.

So, expiring leases help the system recover.

Suppose a worker acquires a lock and then crashes. If the lock never expires, the system may be stuck forever. No one else can continue.

With lease-based locking -

    Lock is held for limited time
    Owner must renew it
    If renewal stops, lock expires
    Another node can acquire it later

This is one of the most common patterns in distributed coordination.

# HOW DISTRIBUTED LOCKS ARE IMPLEMENTED?

Distributed locks are usually implemented using some shared coordination system like -

    Databases
    Redis
    ZooKeeper
    etcd
    Consul

The basic pattern is often something like -

    Try to create a lock record atomically
    If creation succeeds, lock is acquired
    If it already exists, lock is not acquired

    OR

    Acquire lease with expiration time
    Renew it while doing work
    Release it when done

The exact mechanism depends on the system.

Distributed locking is harder than local locking because distributed systems have failures and uncertainty. For example -

    Network delays
    Node crashes
    Lock renewal failure
    Clock differences
    Partitioned network
    Duplicate retries
    Uncertain ownership during failure

Suppose this happens -

    Node A acquires lock
    Network partition happens
    Node A cannot renew
    Lock expires
    Node B acquires lock
    Node A still believes it owns the lock

Now two nodes may both think they are allowed to act. This is a dangerous situation. This is why distributed locking is tricky.

## SPLIT-BRAIN RISK

One of the big dangers in distributed locking is split brain style behavior. This means two nodes both behave as if they own the same responsibility.

For example -

    Old owner thinks lock is still valid
    New owner acquires lock after expiry
    Both continue acting

This can cause duplicate writes or conflicting work.

So, distributed locks must be designed with failure scenarios in mind.

## FENCING TOKENS

One technique used in stronger distributed locking systems is fencing tokens.

A fencing token is a monotonically increasing number given when the lock is acquired.

For example -

    Node A gets token 5
    Later Node B gets token 6

Now, downstream systems can reject stale owners. For example, if Node A later tries to write with token 5 after Node B has already the token 6, the system can reject Node A as stale.

This is a very important idea because lock ownership in distributed systems can become ambiguous during failures. 

A simple lock by itself is not always enough.

# WHEN DISTRIBUTED LOCKING IS USEFUL?

It is useful when -

    1. Only one node should do a task
    2. Duplicate work is dangerous
    3. Shared resource access needs coordination
    4. Leader-only behavior is required
    5. Scheduled or singleton jobs need protection

Examples -

    Cron job execution in many instances
    Inventory sync worker
    Payment settlement task
    Leader-only background cleanup
    Resource migration step

# WHEN TO AVOID DISTRIBUTED LOCKING?

Distributed locking is useful, but it should not be the first solution everywhere. Sometimes better alternatives exist.

For example -

    Partition work so locks are not needed
    Use idempotency so duplicate work is safe
    Use optimistic concurrency control
    Use database constraints
    Use queue semantics where one consumer gets the task

Locks add coordination complexity.

So, if the system can be designed to avoid global shared locking, that is often better. This is an important architectural lesson.
