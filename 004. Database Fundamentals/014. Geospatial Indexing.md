# THE PROBLEM

Many apps need to answer a question like this -

    "Show me all restaurants within 2 km of my location"

Each restaurant has a latitude and longitude. A normal index (like B-tree) does not work well here.

Why? Because location has TWO values (lat and long). A B-tree can sort by one value well. If we index latitude, we can find rows in a latitude range, but we still have to scan all those rows to check longitude.

    Restaurants at latitude 28.6   -> could be in Delhi or in some other country far east or west

So, we need an index that understands that nearby places should be stored close to each other.

There are 3 popular ideas for this - Geohash, Quadtree, and S2 / H3 cells.

# GEOHASH

Geohash converts a lat and long into a short string. The earth is divided into a grid, and each grid cell gets a code. Then each cell is divided again, and the code gets longer.

    Longer string -> smaller area -> more precise

For example -

    "ttnf"    -> a big area (a city)
    "ttnfv2"  -> a smaller area (a few neighbourhoods)
    "ttnfv2u" -> a very small area (a street)

The key point is that places that are near each other usually share the same prefix.

So, to find nearby places -

    1. Convert my location to a geohash
    2. Search for all places with the same prefix (a simple index lookup)
    3. Also check the neighbouring cells
    4. Calculate the real distance and filter

We need step 3 because two places that are very close can sit on two sides of a cell border, and have totally different prefixes.

Geohash is easy to store in any database, because it is just a string. We can use a normal index on it. Redis and many databases use this idea.

# QUADTREE

A quadtree divides the map into 4 squares. If a square has too many places, it is divided into 4 more squares. And so on.

    Whole map
    ├── Top left
    ├── Top right
    ├── Bottom left
    └── Bottom right  (too crowded -> split again)
        ├── ...
        └── ...

So, a crowded area like a big city gets divided into many small squares. An empty area like a desert stays as one big square.

That is the main advantage. The cells adapt to how dense the data is.

To find nearby places, we go down the tree to the square of my location, then look at that square and its neighbours.

Quadtrees are usually kept in memory, so they are fast. But they are harder to store in a normal database and to update when places move.

# GEOHASH VS QUADTREE

    Geohash:
        Fixed size grid
        Just a string, easy to store and index in any database
        Easy to shard by prefix
        Cells can be uneven in dense or empty areas

    Quadtree:
        Cell size adapts to density
        Better for uneven data (cities vs villages)
        Usually an in-memory structure
        Needs more work to keep updated

# S2 AND H3

Google S2 and Uber H3 are modern versions of the same idea. They split the earth into cells (S2 uses squares, H3 uses hexagons) and give each cell an ID.

H3 hexagons are nice because all the neighbours are at an equal distance from the centre. That is useful for things like ride pricing by area.

# WHEN TO USE WHICH

    Nearby search in a database          -> Geohash or a database with built in geo support (PostGIS, Redis GEO)
    Dense in-memory search               -> Quadtree
    Large scale like Uber or Google Maps -> H3 or S2

# SIMPLE EXAMPLE

    Yelp style "restaurants near me"

    1. Store each restaurant with its geohash
    2. User opens the app -> compute the geohash of the user
    3. Query the index for the same prefix and neighbouring prefixes
    4. Calculate the exact distance for the few results
    5. Sort by distance or rating and return

So, the index narrows down millions of places to a few hundred. Then we do the exact maths only on those.
